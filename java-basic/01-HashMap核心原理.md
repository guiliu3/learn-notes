# 01-HashMap核心原理

## 1. 面试先给结论

`HashMap` 是 Java 中最常用的 Map 实现，底层核心是数组 + 链表 + 红黑树。它通过 key 的 hash 值定位数组下标，发生哈希冲突时使用链表或红黑树存储多个节点。

面试表达可以这样说：

> HashMap 底层是数组加链表加红黑树。put 时先根据 key 的 hash 值计算数组下标，如果该位置为空就直接放入；如果有冲突，就比较 key 是否相同，相同则覆盖，不同则挂到链表或红黑树上。JDK 8 之后，当链表长度达到 8 且数组容量达到 64 时，链表会转成红黑树，降低极端冲突下的查询复杂度。

## 2. HashMap 数据结构

JDK 8 之后：

```text
HashMap
  table 数组
    Node<K,V>
      key
      value
      hash
      next
```

冲突较少时：

```text
数组 + 链表
```

冲突严重时：

```text
数组 + 红黑树
```

## 3. put 流程

简化流程：

1. 判断 table 是否初始化，没有则初始化。
2. 根据 key 计算 hash。
3. 根据 `(n - 1) & hash` 计算数组下标。
4. 如果当前位置为空，直接创建节点。
5. 如果当前位置不为空：
   - key 相同，覆盖 value。
   - key 不同，追加到链表或红黑树。
6. 如果链表长度达到阈值，尝试树化。
7. 插入后 size 增加，超过阈值则扩容。

面试表达：

> put 的核心是先算 hash，再定位数组下标。如果没有冲突直接插入；如果有冲突，就在链表或红黑树里查找 key，相同覆盖，不同新增。插入后如果超过扩容阈值，会进行 resize。

## 4. get 流程

简化流程：

1. 根据 key 计算 hash。
2. 根据 hash 定位数组下标。
3. 判断第一个节点是否匹配。
4. 如果不匹配：
   - 链表则遍历链表。
   - 红黑树则按树查找。
5. 找到返回 value，找不到返回 null。

## 5. 为什么容量是 2 的幂

HashMap 数组长度始终是 2 的幂。

原因：

```java
index = (n - 1) & hash
```

当 `n` 是 2 的幂时，`n - 1` 的二进制低位全是 1，可以更高效地计算下标。

好处：

- 位运算比取模更快。
- 下标分布更均匀。
- 扩容迁移更高效。

面试表达：

> HashMap 使用 `(n - 1) & hash` 计算下标，所以容量必须是 2 的幂。这样既能用位运算替代取模，也能让 hash 分布更均匀。扩容时节点要么留在原位置，要么移动到原位置加旧容量的位置。

## 6. 扩容机制

默认参数：

```text
默认初始容量：16
默认负载因子：0.75
扩容阈值：capacity * loadFactor
```

当元素数量超过阈值时，容量扩大为原来的 2 倍。

例如：

```text
容量 16，阈值 12
size > 12 后扩容到 32
```

扩容代价：

- 创建新数组。
- 迁移旧元素。
- 重新分布节点。

所以如果能预估容量，最好初始化合适大小，减少扩容。

## 7. JDK 8 扩容优化

JDK 8 中，扩容时不需要重新计算完整 hash。

节点位置只有两种：

```text
原下标
原下标 + oldCap
```

判断依据：

```java
(hash & oldCap) == 0
```

如果为 0，留在原位置；否则移动到原位置 + oldCap。

## 8. 树化条件

链表转红黑树条件：

```text
链表长度 >= 8
数组容量 >= 64
```

如果链表长度达到 8，但数组容量小于 64，优先扩容，不树化。

原因：

> 容量较小时，冲突可能是数组太小导致的，扩容比树化更合适。

红黑树退化为链表：

```text
节点数 <= 6
```

为什么树化是 8，退化是 6：

- 避免频繁树化和链表化。
- 中间留缓冲区。

## 9. HashMap 是否线程安全

`HashMap` 不是线程安全的。

多线程问题：

- put 数据丢失。
- size 统计不准。
- 扩容时结构异常。
- 并发修改导致不可预期结果。

JDK 7 中多线程扩容可能形成环形链表，导致 get 死循环。JDK 8 改了尾插法，降低了这个特定风险，但 HashMap 仍然不是线程安全的。

面试表达：

> HashMap 不能在多线程写场景下直接使用。JDK 8 虽然解决了 JDK 7 扩容头插法可能导致链表成环的问题，但并发 put 仍然可能数据覆盖、丢失和 size 不准。多线程场景应使用 ConcurrentHashMap。

## 10. hash 方法为什么要高低位扰动

JDK 8 中 hash 处理类似：

```java
h ^ (h >>> 16)
```

目的：

- 让高 16 位参与低位运算。
- 减少低位 hash 不均导致的冲突。

因为数组下标计算主要使用低位：

```java
(n - 1) & hash
```

如果只看低位，hashCode 高位差异无法影响下标。

## 11. equals 和 hashCode 的关系

规则：

- 两个对象 `equals` 为 true，则 `hashCode` 必须相同。
- 两个对象 `hashCode` 相同，`equals` 不一定 true。

如果重写 equals 不重写 hashCode，会导致 HashMap 查找异常。

示例：

```text
put 时按 hashCode 定位到 A 桶
get 时 hashCode 不一致，定位到 B 桶
即使 equals 相同，也找不到
```

## 12. 高频问题

### 12.1 HashMap 底层结构是什么

答法：

> JDK 8 的 HashMap 底层是数组、链表和红黑树。数组用于定位桶，冲突时用链表存储，链表过长且数组容量达到 64 时转红黑树。

### 12.2 HashMap put 流程

答法：

> 先根据 key 计算 hash，再用 `(n - 1) & hash` 定位数组下标。如果桶为空直接插入；如果不为空，先判断 key 是否相同，相同覆盖，不同则挂到链表或红黑树。插入后如果 size 超过阈值就扩容。

### 12.3 为什么容量是 2 的幂

答法：

> 因为 HashMap 通过 `(n - 1) & hash` 计算数组下标，容量是 2 的幂时，位运算能替代取模，效率更高，分布也更均匀。

### 12.4 什么时候树化

答法：

> 链表长度达到 8 且数组容量达到 64 时树化。如果容量小于 64，会优先扩容。树节点数量降到 6 左右时会退化成链表。

### 12.5 HashMap 为什么线程不安全

答法：

> 多线程并发 put 可能导致数据覆盖、丢失、size 不准和扩容过程异常。JDK 8 虽然没有 JDK 7 头插法成环的问题，但仍然不是线程安全的。

## 13. 你要背下来的 1 分钟版本

> HashMap 底层是数组加链表加红黑树。put 时根据 key 的 hash 计算数组下标，如果桶为空直接插入，有冲突就比较 key，相同覆盖，不同就放到链表或红黑树中。JDK 8 之后，当链表长度达到 8 且数组容量达到 64 时，会转成红黑树，避免极端冲突下链表查询退化。HashMap 容量是 2 的幂，因为它用 `(n - 1) & hash` 定位下标，效率高且分布更均匀。HashMap 不是线程安全的，多线程写要用 ConcurrentHashMap。
