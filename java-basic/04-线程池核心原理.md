# 04-线程池核心原理

## 1. 面试先给结论

线程池的核心价值是复用线程、控制并发、隔离资源、避免无限创建线程拖垮系统。面试不能只背七个参数，要能讲清楚任务提交流程、队列选择、拒绝策略和项目参数怎么估。

面试表达可以这样说：

> 线程池主要解决线程复用和资源隔离问题。任务提交后，如果工作线程数小于核心线程数，会优先创建核心线程；否则进入阻塞队列；如果队列满了且线程数小于最大线程数，再创建非核心线程；如果还处理不了，就执行拒绝策略。生产中线程池参数要结合任务类型、接口 RT、QPS、CPU 核数和下游资源能力来设置，不能用默认线程池。

## 2. 线程池七个参数

```java
ThreadPoolExecutor(
    int corePoolSize,
    int maximumPoolSize,
    long keepAliveTime,
    TimeUnit unit,
    BlockingQueue<Runnable> workQueue,
    ThreadFactory threadFactory,
    RejectedExecutionHandler handler
)
```

含义：

- corePoolSize：核心线程数。
- maximumPoolSize：最大线程数。
- keepAliveTime：非核心线程空闲存活时间。
- unit：时间单位。
- workQueue：阻塞队列。
- threadFactory：线程工厂。
- handler：拒绝策略。

## 3. 任务提交流程

核心流程：

1. 当前线程数 < corePoolSize：创建核心线程执行任务。
2. 当前线程数 >= corePoolSize：尝试放入队列。
3. 队列满了，且当前线程数 < maximumPoolSize：创建非核心线程。
4. 线程数达到 maximumPoolSize 且队列也满：执行拒绝策略。

常见误区：

> 不是先创建到最大线程数，再放队列。默认流程是先核心线程，再队列，再最大线程。

## 4. 常见队列

### 4.1 ArrayBlockingQueue

- 有界数组队列。
- 可控制最大积压。
- 生产更推荐有界队列。

### 4.2 LinkedBlockingQueue

- 链表队列。
- 可以有界，也可以无界。
- 如果无界，maximumPoolSize 基本失效，可能导致任务大量堆积。

### 4.3 SynchronousQueue

- 不存储任务。
- 任务必须直接交给线程。
- Executors.newCachedThreadPool 使用它。

### 4.4 PriorityBlockingQueue

- 优先级队列。
- 注意任务排序和饥饿问题。

## 5. 拒绝策略

### 5.1 AbortPolicy

默认策略，直接抛异常。

适合：

- 希望调用方明确感知失败。

### 5.2 CallerRunsPolicy

由提交任务的线程自己执行。

效果：

- 降低提交速度。
- 形成反压。

适合：

- 允许调用方变慢。
- 不希望任务直接丢失。

### 5.3 DiscardPolicy

直接丢弃任务，不抛异常。

风险：

- 任务静默丢失。

### 5.4 DiscardOldestPolicy

丢弃队列最老任务，再提交新任务。

风险：

- 老任务丢失。

面试表达：

> 生产中我很少使用静默丢弃策略，除非业务明确允许。更常见是 AbortPolicy 配合异常处理，或者 CallerRunsPolicy 形成反压。关键任务要记录失败并补偿。

## 6. 为什么不建议用 Executors

`Executors.newFixedThreadPool`：

- 使用无界 LinkedBlockingQueue。
- 任务可能无限堆积，导致 OOM。

`Executors.newCachedThreadPool`：

- maximumPoolSize 接近无限。
- 可能创建大量线程，导致 OOM 或上下文切换严重。

`Executors.newSingleThreadExecutor`：

- 无界队列。
- 任务堆积风险。

建议：

> 使用 ThreadPoolExecutor 显式设置参数，特别是有界队列和拒绝策略。

## 7. CPU 密集型和 IO 密集型

CPU 密集型：

- 主要消耗 CPU。
- 线程数接近 CPU 核数。

IO 密集型：

- 大量等待 DB、Redis、HTTP。
- 线程数可以适当大于 CPU 核数。

但生产不能只靠公式。

还要看：

- 下游数据库连接池。
- Redis 连接池。
- 接口超时时间。
- 平均 RT。
- QPS。
- 机器 CPU 和内存。

## 8. 项目怎么讲

### 8.1 中考查询系统

异步查询或结果生成可以用独立线程池。

设计重点：

- 查询主链路不能被异步任务拖垮。
- 查询线程池和后台任务线程池隔离。
- 队列必须有界。
- 队列满时返回“查询处理中”或限流。

面试表达：

> 中考查询系统高峰期，我会把 Web 请求线程和异步查询线程隔离。线程池队列设置有界，防止任务无限堆积。超过承载能力时，通过 Sentinel 限流或拒绝策略返回查询繁忙，而不是继续堆任务。

### 8.2 数据同步平台

消费者处理、补偿任务、告警通知应使用不同线程池。

设计重点：

- 实时消费和补偿任务隔离。
- 补偿任务不能抢占实时消费资源。
- 写库线程数不能超过数据库承载能力。
- 拒绝后记录失败，进入补偿。

面试表达：

> 数据同步平台里，我会把实时消费、补偿任务、告警通知分到不同线程池，避免补偿任务把实时消费拖慢。线程数要结合数据库连接池和下游接口能力设置，不能只看应用 CPU。

## 9. 高频问题

### 9.1 线程池任务提交流程

答法：

> 先判断工作线程是否小于核心线程数，小于则创建核心线程；否则尝试入队；队列满了且线程数小于最大线程数，则创建非核心线程；如果队列满且达到最大线程数，则执行拒绝策略。

### 9.2 为什么不用 Executors

答法：

> Executors 默认工厂方法容易隐藏无界队列或无限线程数风险，任务堆积可能 OOM。所以生产更推荐直接使用 ThreadPoolExecutor，显式设置线程数、有界队列、线程工厂和拒绝策略。

### 9.3 线程池参数怎么设置

答法：

> 要看任务类型、CPU 核数、QPS、RT、下游资源能力。CPU 密集型接近 CPU 核数，IO 密集型可以适当大一些，但还要受数据库连接池、接口超时、队列长度和机器资源限制。

### 9.4 队列为什么要有界

答法：

> 无界队列会把压力隐藏起来，任务不断堆积，最终可能 OOM 或延迟越来越高。有界队列能让系统在超过承载能力时及时触发拒绝策略，形成保护。

### 9.5 CallerRunsPolicy 有什么作用

答法：

> CallerRunsPolicy 让提交任务的线程自己执行任务，会降低提交速度，形成反压，适合不希望任务直接丢失但允许调用方变慢的场景。

## 10. 你要背下来的 1 分钟版本

> 线程池用于复用线程、控制并发和隔离资源。任务提交后，先创建核心线程，再进入队列，队列满了才创建非核心线程，达到最大线程数后触发拒绝策略。生产中不建议用 Executors，因为可能使用无界队列或无限线程数。线程池参数要结合任务类型、QPS、RT、CPU 核数和下游数据库连接池能力设置。队列必须有界，拒绝策略要结合业务决定，关键任务失败要记录和补偿。
