# AOP原理（JDK动态代理 vs CGLIB）、事务管理（@Transactional失效场景）


## 一、AOP原理

### 1.1 什么是AOP，为什么需要它

AOP（Aspect Oriented Programming，面向切面编程）解决的问题：有些逻辑（日志、事务、权限校验）会散落在很多业务方法里，重复写很烦，而且和核心业务逻辑混在一起，不好维护。

AOP的思路是：把这些"横切关注点"抽出来，单独写成一个"切面"，然后在不修改原始代码的前提下，**在方法执行的前后"插入"这段逻辑**。

一句话记忆：**AOP = 不改源码，运行时动态给方法"加料"**。
> 口语化: AOP是面向切面编程，比如有些业务需要记录请求的前后入参和出参、以及事务处理等，这种若都融合在业务里，则耦合性太高，且大量重复代码，至此我们可以将这些非业务逻辑抽取，
>  Spring 在运行时**动态生成一个代理对象**，**在不修改原有业务代码的基础上**，这些非业务逻辑在实际业务执行的前后插入。

### 1.2 核心术语（面试常问，要能对应上）

| 术语 | 含义 |
|---|---|
| 切面（Aspect） | 横切逻辑的封装，比如"日志切面" |
| 连接点（JoinPoint） | 程序执行过程中能被拦截的点，Spring AOP里特指方法调用 |
| 切点（Pointcut） | 一个表达式，规定"哪些方法"要被拦截，比如 `execution(* com.xxx.service.*.*(..))` |
| 通知（Advice） | 具体要插入的逻辑，分前置/后置/环绕/异常通知等 |
| 织入（Weaving） | 把切面逻辑"嵌入"到目标对象的过程 |


### 1.3 AOP的实现方式：动态代理

Spring AOP的底层实现就是**动态代理**——运行时给目标对象生成一个"代理对象"，代理对象在调用真实方法前后插入切面逻辑。

有两种代理方式，**Spring会自动选择**：

#### JDK动态代理

- **条件**：目标类必须实现了至少一个接口
- **原理**：基于反射，生成一个实现了同样接口的代理类，代理类里持有真实对象的引用，调用接口方法时先执行`InvocationHandler.invoke()`，在里面插入切面逻辑，再调用真实对象的方法
- **本质**：代理对象和目标对象是"兄弟关系"（都实现同一个接口），不是父子关系
>  口语化：JDK动态代理，是目标类至少实现一个接口，通过反射动态生成代理类，代理类持有目标类的引用，而代理类执行真正业务逻辑方法时，可以在前后进行业务增强。代理对象和目标对象都实现了同一个接口。

#### CGLIB动态代理

- **条件**：目标类没有实现接口时使用（也可以强制开启）
- **原理**：基于字节码技术，**生成目标类的一个子类**，重写目标类的方法，在子类方法里插入切面逻辑后再调用父类（也就是目标类）的方法
- **限制**：因为是用继承实现的，所以**目标类不能是final**（无法被继承），**目标方法也不能是final/private/static**（无法被子类重写）
> 口语化：Cglib代理，是通过继承试实现的，通过目标类生成一个子类，重写目标类的方法，在子类方法里插入增强逻辑。增强的方法不能是final等无法被继承的方法。

### 1.4 Spring Boot默认用哪个

**Spring Boot 2.x开始，默认全部使用CGLIB**（即使目标类实现了接口），可以通过配置 `spring.aop.proxy-target-class=false` 改回"有接口用JDK、没接口用CGLIB"的旧策略。

> 面试官常问"为什么默认用CGLIB"：因为统一用CGLIB能避免"同一个项目里一部分Bean是JDK代理、一部分是CGLIB代理"导致的类型转换问题（比如把代理对象强转成实现类类型会报错），统一了行为更可预测。
> 口语化：默认用CGLIB，是因为统一行为，避免类型转换问题。

### 1.5 AOP代理生成的具体时机（和Day1串起来）

回顾Day1讲过的：AOP代理是在Bean生命周期的**`postProcessAfterInitialization`**阶段生成的，具体执行者是`AnnotationAwareAspectJAutoProxyCreator`，它本质是一个`BeanPostProcessor`，在这一步判断该Bean是否匹配某个切点表达式，如果匹配就返回代理对象替换原始对象。

> 口语化：AOP代理发生在Bean生命周期的初始化后的后置处理阶段，通过判断该Bean是否匹配切点。匹配则返回代理对象。否则就是原始对象。

## 二、事务管理（@Transactional）

### 2.1 事务的本质：也是AOP

`@Transactional`本质上**也是通过AOP代理实现的**——Spring会给标了这个注解的方法所在的Bean生成一个代理对象，代理对象在调用真实方法前开启事务，方法执行完后根据是否抛异常决定提交还是回滚。

正因为底层是代理，**所以事务失效的根本原因几乎都可以归结为同一句话：没有经过代理对象调用方法**。
> 口语化： 事务注解，是通过AOP代理实现的，在方法调用前开启事务，然后方法执行后，判断发生异常则回滚事务。

### 2.2 高频失效场景（背熟，这是面试必考）

#### ① 方法内部自调用（最经典的坑）

```java
@Service
public class UserService {
    public void methodA() {
        this.methodB(); // 事务失效！
    }
    
    @Transactional
    public void methodB() {
        // ...
    }
}
```

**原因**：`this.methodB()`是直接调用对象自己的方法，没有经过Spring生成的代理对象，自然不会触发事务逻辑。

> 口语化：方法内部自调用，我可以理解成，比如代理类调用方法A，然后此时事务能生效，但是方法A再在内部调用B，此时属于类的内部方法调用，没有经过spring代理，导致事务失效。

**解决办法**：
- 把`methodB`抽到另一个Bean里，通过注入的方式调用
- 注入自己的代理对象（`AopContext.currentProxy()`，需要开启`exposeProxy=true`）

#### ② 方法不是public

`@Transactional`标注在`private`/`protected`/默认（包级）方法上**不生效**。

**原因**：Spring AOP的代理机制（无论JDK还是CGLIB）都是基于"方法重写/接口实现"，非public方法无法被正常代理拦截到。

#### ③ 异常被自己catch了，没有往外抛

```java
@Transactional
public void methodA() {
    try {
        // 业务逻辑
    } catch (Exception e) {
        log.error("出错了", e); // 吞掉异常，事务不会回滚！
    }
}
```

**原因**：Spring事务通过"是否捕获到异常"来判断要不要回滚，如果你自己在方法内部把异常catch住、没有重新抛出，代理感知不到异常，事务照样提交。

**解决办法**：catch住之后手动调用 `TransactionAspectSupport.currentTransactionStatus().setRollbackOnly()`，或者直接把异常重新抛出去。

#### ④ 抛出的异常类型不对

默认情况下`@Transactional`只对**`RuntimeException`和`Error`**回滚，对**受检异常（Checked Exception，比如`IOException`）不会回滚**。

**解决办法**：在注解里指定 `@Transactional(rollbackFor = Exception.class)`，显式声明要回滚的异常类型。

#### ⑤ 类没有被Spring管理，或者方法所在类没加事务注解的类没被代理

比如`@Transactional`加在一个没有被`@Service`/`@Component`等注解标记、没纳入Spring容器管理的类上，自然不会生效——因为Spring压根没给它生成代理对象。

#### ⑥ 多线程场景

事务是绑定在**当前线程**的（基于`ThreadLocal`存储数据库连接），如果方法内部开了新线程去执行业务逻辑，新线程里的操作和当前事务**不是一个事务**，不会一起提交或回滚。

#### ⑦ 数据库引擎不支持事务

最容易被忽略的一点：如果用的是MySQL的**MyISAM引擎**（不支持事务，只有InnoDB支持），那无论代码怎么写，事务都不会生效。

### 2.3 事务传播机制（了解即可，不用死记每一种）

`@Transactional(propagation = ...)` 常见的几种：

- **REQUIRED（默认）**：如果当前已经有事务，就加入这个事务；没有就新建一个
- **REQUIRES_NEW**：无论当前有没有事务，都新开一个独立事务（原来的事务会被挂起）
- **NESTED**：嵌套事务，子事务可以单独回滚而不影响外部事务

> 面试官一般问到REQUIRED和REQUIRES_NEW的区别就够了，不需要把7种全背下来。

## 三、Day1+Day2 串联记忆

把这两天的内容串起来，会发现是一条完整的链路：

> **IOC容器创建Bean → 生命周期走到`postProcessAfterInitialization`阶段 → AOP判断是否需要代理（动态代理：JDK或CGLIB）→ 如果用了`@Transactional`，本质就是生成了一个"事务代理对象" → 事务失效的各种坑，几乎都是因为"没有经过这个代理对象去调用方法"**

记住这条链路，事务和AOP的题基本可以一通百通。
