# 07-主从延迟与数据一致性

## 1. 面试先给结论

MySQL 主从复制主要用于读写分离、容灾备份和高可用，但它默认是异步复制，天然可能存在主从延迟。

面试表达可以这样说：

> 主从复制可以提高读能力和可用性，但不能简单认为写主库后从库立刻可见。因为主库提交事务后，需要把 binlog 传给从库，从库再执行 relay log，这个过程可能有延迟。所以涉及写后立刻读、支付状态、同步状态这类强一致场景，不能随便读从库，需要读主库、延迟检测或业务补偿。

## 2. 主从复制解决什么问题

常见用途：

- 读写分离。
- 查询扩展。
- 数据备份。
- 故障切换。
- 报表查询隔离。
- 降低主库读压力。

典型架构：

```text
应用写入 -> 主库
应用查询 -> 从库
主库 binlog -> 从库 relay log -> 从库回放
```

注意：

> 主从不是为了让数据库写入能力无限提升。写请求通常仍然打到主库，主从更多提升读能力和可用性。

## 3. 主从复制基本流程

简化流程：

1. 主库提交事务，写入 binlog。
2. 从库 IO 线程拉取主库 binlog。
3. 从库写入 relay log。
4. 从库 SQL 线程回放 relay log。
5. 从库数据追上主库。

复制链路：

```text
Master binlog -> Slave IO Thread -> relay log -> Slave SQL Thread -> data
```

## 4. 为什么会有主从延迟

主从延迟本质是：

> 主库产生 binlog 的速度，大于从库拉取和回放的速度。

常见原因：

- 主库写入量突然增大。
- 从库机器配置较弱。
- 从库 SQL 回放慢。
- 大事务。
- DDL 操作。
- 从库执行慢 SQL 或报表查询。
- 网络延迟。
- 从库单线程回放瓶颈。
- 表缺少主键或索引，导致回放慢。

## 5. 主从延迟会造成什么问题

### 5.1 写后读不一致

用户刚提交数据，立刻查询却查不到。

```text
写主库成功 -> 立即读从库 -> 从库还没同步 -> 查不到
```

### 5.2 状态判断错误

例如数据同步平台：

```text
刚把同步状态更新为 success
管理端读从库
从库还没同步
页面仍显示 processing
```

### 5.3 重复处理

补偿任务读从库，发现状态还是未同步，可能重复发消息。

### 5.4 分页和统计不准

主从延迟会导致列表、统计数量和详情状态不一致。

## 6. 如何判断主从延迟

常见方式：

```sql
SHOW SLAVE STATUS\G
```

或新版本：

```sql
SHOW REPLICA STATUS\G
```

关注：

- Seconds_Behind_Master。
- Slave_IO_Running。
- Slave_SQL_Running。
- Relay_Log_Pos。
- Exec_Master_Log_Pos。
- Last_Error。

注意：

> Seconds_Behind_Master 只能作为参考，不是绝对精确。生产中还需要结合监控、心跳表、业务延迟指标判断。

## 7. 主从延迟怎么处理

### 7.1 写后读主库

适合场景：

- 用户提交后立刻查看。
- 同步状态更新后立刻查询。
- 订单支付后查看状态。
- 权限变更后立即生效。

策略：

```text
写操作后短时间内强制读主库
```

例如：

```text
提交同步重推 -> 立即查询该批次状态 -> 读主库
```

### 7.2 延迟检测后决定读哪里

如果主从延迟超过阈值：

- 暂时读主库。
- 降级提示。
- 暂停报表查询。
- 限制补偿任务。

### 7.3 业务上接受最终一致

不是所有查询都要强一致。

可接受从库延迟的场景：

- 报表统计。
- 历史列表。
- 非实时看板。
- 后台低频查询。

不可接受延迟的场景：

- 支付状态。
- 权限变更。
- 同步补偿状态判断。
- 创建后立即查询。

### 7.4 避免大事务

大事务会导致从库回放慢。

优化：

- 批量任务分批提交。
- 避免一次更新大量数据。
- 控制单事务大小。
- 避免长时间持锁。

### 7.5 优化从库回放性能

方向：

- 从库配置不要太弱。
- 表必须有主键。
- 更新条件命中索引。
- 开启并行复制。
- 避免从库跑重报表影响复制。

## 8. 读写分离注意事项

读写分离不是简单把所有 SELECT 都走从库。

要分类：

强一致读：

- 读主库。
- 或使用强制主库标记。

最终一致读：

- 可以读从库。

报表查询：

- 优先读从库或专门报表库。

高风险查询：

- 深分页、大范围统计、大报表不要影响主库。

面试表达：

> 我不会把所有查询都默认切到从库。涉及写后读、状态判断、补偿扫描这类场景要谨慎，必要时读主库。报表、历史列表、非实时统计可以读从库。

## 9. 半同步复制

MySQL 默认异步复制：

```text
主库提交事务后，不等待从库确认。
```

半同步复制：

```text
主库提交时，至少等待一个从库接收到 binlog 后再返回。
```

价值：

- 降低主库宕机导致数据丢失的风险。

限制：

- 不等于从库已经执行完成。
- 仍可能存在读延迟。
- 性能比异步复制有损耗。

面试表达：

> 半同步复制能降低数据丢失风险，但不能完全解决读写一致性问题。因为它通常保证至少有从库收到日志，不代表从库已经回放完成。

## 10. 主从切换风险

主库故障后可能进行主从切换。

风险：

- 从库数据未追平。
- 新主库数据缺失。
- 应用连接未及时切换。
- 自增 ID 或数据冲突。
- 旧主恢复后脑裂。

处理原则：

- 使用成熟高可用方案。
- 切换前确认复制位点。
- 防止双主写入。
- 应用层做好重试。
- 关键业务有补偿校验。

## 11. 项目一：中考查询系统如何使用主从

中考查询系统读多写少，适合读写分离。

适合读从库：

- 成绩查询。
- 学校维度查询。
- 历史查询记录。
- 报表统计。

需要注意：

- 成绩发布前数据导入完成后，要确认主从同步完成。
- 查询开放前可以做缓存预热。
- 如果刚导入后从库未追平，不能立即开放查询。
- 高峰查询优先走 Redis，数据库作为兜底。

面试表达：

> 中考查询系统读多写少，理论上适合读写分离。但成绩导入后不能立刻假设从库已同步完成，需要在开放查询前确认主从延迟为 0 或在可接受范围内，再做缓存预热。查询高峰期优先走 Redis，数据库作为兜底，避免从库也被打满。

## 12. 项目二：数据同步平台如何处理主从延迟

数据同步平台更容易被主从延迟影响。

高风险场景：

- 业务源刚写入，消费者从从库查询源数据，可能查不到。
- 同步状态刚更新，管理端读从库，状态不一致。
- 补偿任务读从库扫描未同步数据，可能重复补偿。
- 消费者根据从库状态判断是否已同步，可能误判。

处理建议：

- 消费者读取源业务数据优先读主库或保证延迟可控。
- 补偿扫描状态表优先读主库。
- 写后立刻读的状态查询读主库。
- 管理端历史列表可以读从库。
- 幂等主键和唯一索引兜底重复处理。
- 补偿任务要有状态机和更新时间窗口。

面试表达：

> 数据同步平台不能简单把所有查询都读从库。比如消费者收到 Kafka 消息后，要根据业务主键查源数据，如果这时源数据刚提交而从库还没同步，读从库可能查不到，导致误判失败。所以核心同步链路和补偿扫描更适合读主库，历史查询和报表可以读从库。即使读主库，也要通过幂等主键、唯一索引和补偿任务保证最终一致。

## 13. 补偿任务与主从延迟

补偿任务常见写法：

```sql
SELECT *
FROM sync_record
WHERE status IN ('pending', 'failed')
  AND update_time < NOW() - INTERVAL 5 MINUTE
LIMIT 100;
```

为什么要加时间窗口：

- 避免刚写入的数据还没完成状态流转就被补偿。
- 避免主从延迟导致误扫。
- 给正常消费留出处理时间。

还要注意：

- 使用状态机。
- 加最大重试次数。
- 加版本号或乐观锁。
- 分批扫描。
- 避免多个补偿任务重复抢同一批数据。

## 14. 高频问题

### 14.1 MySQL 主从复制流程

答法：

> 主库提交事务后写 binlog，从库 IO 线程拉取 binlog 写入 relay log，从库 SQL 线程再回放 relay log，最终让从库数据追上主库。

### 14.2 为什么会有主从延迟

答法：

> 因为主库产生 binlog 的速度超过从库拉取和回放速度。常见原因包括大事务、写入量突增、从库性能差、DDL、网络延迟、从库执行慢 SQL、表缺少主键或索引等。

### 14.3 写后立刻读怎么处理

答法：

> 写后立刻读通常要读主库，或者在短时间内强制读主库。因为读从库可能遇到主从延迟，导致刚写的数据查不到。

### 14.4 半同步复制能解决主从延迟吗

答法：

> 不能完全解决。半同步主要降低主库宕机导致数据丢失的风险，它通常保证至少一个从库收到日志，但不代表从库已经回放完成，所以读从库仍可能有延迟。

### 14.5 数据同步平台为什么要关注主从延迟

答法：

> 因为消费者收到消息后可能马上查源数据，如果读从库而从库没同步，就会查不到；补偿任务如果读从库，也可能误判状态，导致重复补偿。所以核心同步链路和补偿扫描要谨慎读从库，通常读主库或加延迟窗口。
