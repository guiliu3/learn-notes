一、锁的分类
1. 按粒度分
- 表锁（Table Lock）：锁住整张表，并发度低。
- 行锁（Row Lock）：锁住具体的行，并发度高，InnoDB默认行锁。
- 页锁（Page Lock）：锁住一个数据页（16kb）

说明：粒度越小，并发越高，但是加锁开销越大；粒度越大，并发越低，加锁开销越小。

2. 按模式分
- 共享锁 S锁（读锁）：我在读，别人也可以读，但不能改
- 排他锁 X锁（写锁）：我在写，别人既不能读（当前读），也不能写

  说明：只有读读之间兼容，只要有写就互斥。
```mysql
-- 加共享锁（S锁）
SELECT * FROM orders WHERE id = 1 LOCK IN SHARE MODE;

-- 加排它锁（X锁）
SELECT * FROM orders WHERE id = 1 FOR UPDATE;

-- 普通 UPDATE / DELETE / INSERT 自动加排它锁
UPDATE orders SET amount = 200 WHERE id = 1;
```  


3. 意向锁（IS / IX）
- 是什么，为什么需要它
  - ep:
     - 事务A 对某一行加了行级 X 锁
     - 事务B 想对整张表加表锁

    问题：B 怎么知道表里有没有行被锁住？
     - 没有意向锁：B 必须逐行检查，全表扫一遍 → 代价极大
     - 有意向锁：A 加行锁时，顺便在表上加一个意向锁 ,B 只需检查表上有没有意向锁，O(1) 判断

  - 意向共享锁 IS：事务准备对某行加 S 锁前，先在表上加 IS 锁
  - 意向排他锁 IX：事务准备对某行加 X 锁前，先在表上加 IX 锁
  - 意向锁是 InnoDB 自动加的，业务代码感知不到。


4. 乐观锁 vs 悲观锁
   - 乐观锁：版本号/CAS，非真实锁
     - 说明：假设冲突很少发生，不加锁，提交时再检查有没有冲突
     - 加锁：
        ```mysql
           -- 表里加一个 version 字段
             SELECT id, stock, version FROM product WHERE id = 1;
           -- 假设读到 stock=100, version=5

            -- 更新时带上 version 条件
              UPDATE product
               SET stock = stock - 1, version = version + 1
              WHERE id = 1 AND version = 5;

            -- 影响行数 = 0，说明期间有人改过，重试或报错
            -- 影响行数 = 1，说明没有冲突，更新成功 
       ```
       适合读多写少、冲突概率低的场景。
     
- 悲观锁：SELECT FOR UPDATE
  - 说明：假设冲突一定发生，每次操作都加锁
  - 加锁：
    ```mysql
          -- 用 FOR UPDATE 实现悲观锁
             BEGIN;
             SELECT * FROM order WHERE id = 1 FOR UPDATE;  -- 加 X 锁
          -- 处理业务...
             UPDATE order SET status = 2 WHERE id = 1;
             COMMIT;
    ```
    适合写多、冲突概率高的场景。


二、InnoDB 行锁类型（重点）
1. Record Lock（记录锁）—— 锁单行
   - 说明：InnoDB 的数据在物理上是按照**主键索引（聚簇索引）**组织存储的，数据行本身就挂在主键索引的叶子节点上。所以锁索引记录，本质上就是锁住了这个索引节点，进而保护了对应的数据行。
   - 备注：记录锁 ≈ 行锁

2. Gap Lock（间隙锁）  —— 锁范围，防止插入
   在事务与MCC机制介绍过

3. Next-Key Lock       —— Record + Gap，InnoDB 默认
   - 说明：就是 Record Lock + Gap Lock 的组合，锁住某一行以及这一行左边的间隙，是 InnoDB 在 RR 级别下的默认加锁方式。
   
4. 插入意向锁          —— INSERT 时加，与 Gap Lock 冲突
   

三、加锁规则（面试核心）
1. 基本原则
- 查询用到的索引才加行锁，否则锁全表
- 加锁单位是 Next-Key Lock
- 加锁具体情况，Next-Key Lock 会退化为Record Lock 或者Gap Lock

2. 等值查询加锁分析
- 唯一索引命中：退化为 Record Lock
  
  - id 是主键，表中有 id：1, 5, 10, 20
  - ep:
  ```mysql
    
    SELECT * FROM user WHERE id = 5 FOR UPDATE;
    -- 加锁：Record Lock [5]
    -- 只锁 id=5 这一行，间隙不锁
    -- 其他事务可以插入 id=3、id=7


- 唯一索引未命中：退化为 Gap Lock
- id 是主键，表中有 id：1, 5, 10, 20
  - ep:
   ```mysql
    -- 表中没有 id=6
     SELECT * FROM user WHERE id = 6 FOR UPDATE;

    -- id=6 落在 (5, 10) 间隙内
    -- 加锁：Gap Lock (5, 10)
    -- 锁住间隙，防止插入 id=6 附近的数据
    -- 不锁 id=5 和 id=10 本身
   ```

- 普通索引命中：Next-Key Lock + 下一个间隙 Gap Lock
 - ep:
   ```mysql
      -- age 是普通索引，表中 age 有：10, 20, 20, 30
        SELECT * FROM user WHERE age = 20 FOR UPDATE;
    
      -- 加锁：
      -- Next-Key Lock (10, 20]   ← 锁住命中记录及左边间隙
      -- Gap Lock (20, 30)        ← 额外锁住右边间隙（防止插入 age=20 的新记录）
   ```
  - 为什么要锁右边间隙？
    其他事务可以插入 age=20 的新行，当前读会出现幻读

3. 范围查询加锁分析
- 唯一索引范围查询
 - ep:
  ```mysql
    -- 表中有 id：1, 5, 10, 20
      SELECT * FROM user WHERE id >= 5 AND id < 10 FOR UPDATE;
    
    --  扫描过程：
    --  找到 id=5  → Next-Key Lock (1, 5]  → 唯一索引优化，退化为 Record Lock [5]
    --  找到 id=10 → Next-Key Lock (5, 10] → 但条件是 id < 10，10 不满足
    --  退化为 Gap Lock (5, 10)
    
    --  最终加锁：
    --  Record Lock [5]
    --  Gap Lock (5, 10)
  ```
  
- 普通索引范围查询
  - ep:
  ```mysql
    -- age 是普通索引，表中 age：10, 20, 30, 40
    SELECT * FROM user WHERE age >= 20 AND age < 30 FOR UPDATE;
    -- 扫描过程：
    -- 找到 age=20 → Next-Key Lock (10, 20]
    -- 找到 age=30 → 超出范围，但扫到了 30 → Next-Key Lock (20, 30]

    --   最终加锁：
    -- Next-Key Lock (10, 20]
    -- Next-Key Lock (20, 30]

    -- 合并区间：(10, 30]
  ```

4. 无索引查询：锁全表（升级为表锁）
  - ep:
    ```mysql
         -- name 没有索引
         SELECT * FROM user WHERE name = '张三' FOR UPDATE;
    ```
  - InnoDB只能全表扫描，每一行都加Next-Key Lock= 锁住全表全部间隙和记录 =等同于表锁
  - 其他事务对这张表的任何 INSERT/UPDATE/DELETE 全部阻塞


四、死锁
### 1. 死锁产生的四个必要条件
  - 互斥：一个资源同时被一个事务持有
  - 占有并等待：事务持有锁的同时，等待其他锁
  - 不可剥夺：已持有锁不能被强制释放
  - 循环等待：事务A等待B，事务B等A，形成环。
  - ep:
  ```text
     -- 表中有 id=1，id=2
     --  事务A                              事务B
        BEGIN;                             BEGIN;
        UPDATE user SET .. WHERE id=1;     UPDATE user SET .. WHERE id=2;
        -- A 持有 id=1 的锁                 -- B 持有 id=2 的锁
        
        UPDATE user SET .. WHERE id=2;     UPDATE user SET .. WHERE id=1;
        -- A 等待 id=2（B持有）             -- B 等待 id=1（A持有）
        
        互相等待 → 死锁！

  ```   

### 2. InnoDB 死锁检测（innodb_deadlock_detect）
  - InnoDB 有自动死锁检测机制（默认开启）： innodb_deadlock_detect = ON  （默认）

  - 检测到死锁时：
    - 自动选择一个代价最小的事务回滚（通常是 undo log 量少的）
    - 被回滚的事务报错：ERROR 1213: Deadlock found
    - 另一个事务继续执行

  - 死锁检测的代价：
      高并发时，每个新锁请求都要遍历等待图检测是否成环，线程越多代价越高。极端场景下死锁检测本身会成为性能瓶颈。

  - innodb_deadlock_detect = OFF  -- 关掉检测，用锁超时代替
  - innodb_lock_wait_timeout = 50 -- 默认50秒，等待超时自动回滚

### 4. 避免死锁的实践方案
  - 缩短事务，减少持锁时间
  - 降低隔离级别： RC 级别没有 Gap Lock，减少间隙锁冲突，降低死锁概率。
  - 避免大事务：大事务持有锁多、时间长，与其他事务冲突概率高。拆分成小事务。
  - 合理使用索引：无索引 → 锁全表 → 与所有事务冲突 → 死锁概率大增。
  - 超时兜底：-- 不依赖死锁检测，超时自动回滚
