# 06-慢SQL与线上排查

## 1. 面试先给结论

慢 SQL 排查不能只说“加索引”，而是要从现象、范围、SQL、执行计划、索引、锁等待、连接池、数据量、业务调用链路几个层面定位。

面试表达可以这样说：

> 我排查慢 SQL 一般先确认是单个接口慢，还是整个数据库慢；再看慢日志、监控、连接池、CPU、IO、锁等待等指标。定位到具体 SQL 后，用 EXPLAIN 看执行计划，判断索引是否命中、扫描行数是否过大、是否出现 filesort、temporary。最后结合业务场景优化 SQL、索引、分页、缓存或表结构，而不是一上来就盲目加索引。

## 2. 慢 SQL 常见表现

线上常见现象：

- 接口 RT 突然升高。
- 请求大量超时。
- 数据库连接池接近打满。
- CPU 升高。
- 磁盘 IO 升高。
- 慢查询日志增加。
- 线程堆栈大量卡在 JDBC 查询。
- Sentinel 或 Gateway 开始大量限流。
- Redis 命中率下降后，DB 压力升高。

面试中要注意：

> 慢 SQL 不一定是 SQL 本身写得差，也可能是缓存失效、请求量突增、锁等待、连接池不足、数据倾斜、索引失效造成的。

## 3. 排查优先级

### 3.1 先判断影响范围

先问几个问题：

- 是单个接口慢，还是所有接口慢？
- 是单个服务慢，还是多个服务都慢？
- 是某个时间点突然慢，还是一直慢？
- 是读慢，还是写慢？
- 是偶发慢，还是持续慢？
- 是否刚发布、刚改 SQL、刚改索引、刚改配置？

如果所有接口都慢，优先看数据库整体资源、连接池、锁等待。

如果只有一个接口慢，优先定位该接口对应 SQL 和调用链。

### 3.2 看监控指标

数据库侧：

- CPU。
- 内存。
- 磁盘 IO。
- QPS/TPS。
- 活跃连接数。
- 慢查询数量。
- 锁等待。
- 临时表。
- 主从延迟。

应用侧：

- 接口 RT。
- 错误率。
- Tomcat 线程。
- 业务线程池。
- 数据库连接池活跃连接数。
- Redis 命中率。
- GC。

### 3.3 定位具体 SQL

来源：

- MySQL 慢查询日志。
- APM 链路追踪。
- 应用日志 traceId。
- 数据库审计。
- 连接池监控。

定位后不要只看 SQL 文本，还要看：

- 入参是什么。
- 返回行数多少。
- 调用频率多高。
- 是否被循环调用。
- 是否因为分页过深。
- 是否是批量任务。

## 4. 慢查询日志

慢查询日志用于记录执行时间超过阈值的 SQL。

常见配置：

```sql
SHOW VARIABLES LIKE 'slow_query_log';
SHOW VARIABLES LIKE 'long_query_time';
SHOW VARIABLES LIKE 'log_queries_not_using_indexes';
```

常见关注：

- Query_time：执行耗时。
- Lock_time：锁等待时间。
- Rows_sent：返回行数。
- Rows_examined：扫描行数。

判断重点：

> Rows_examined 很大但 Rows_sent 很小，通常说明扫描了大量无效数据，可能索引不合理或条件过滤性差。

## 5. EXPLAIN 怎么看

常用命令：

```sql
EXPLAIN SELECT * FROM sync_record WHERE biz_id = 'A001';
```

重点字段：

- type。
- possible_keys。
- key。
- key_len。
- rows。
- filtered。
- Extra。

### 5.1 type

从好到差大致是：

```text
system > const > eq_ref > ref > range > index > ALL
```

常见判断：

- `const`：主键或唯一索引等值查询，通常很好。
- `ref`：普通索引等值查询，通常可以接受。
- `range`：范围扫描。
- `index`：扫描整个索引。
- `ALL`：全表扫描，重点关注。

### 5.2 key

`key` 表示实际使用的索引。

如果 `possible_keys` 有值，但 `key` 为空，说明优化器没有选择索引。

常见原因：

- 条件选择性差。
- 使用函数导致索引失效。
- 隐式类型转换。
- like 前缀通配。
- 数据量太小。
- 统计信息不准确。

### 5.3 rows

`rows` 是优化器预估扫描行数。

如果 rows 很大，要重点看：

- 是否缺索引。
- 联合索引顺序是否合理。
- 查询条件是否有效过滤。
- 是否分页过深。

### 5.4 Extra

重点关注：

- Using index：覆盖索引，通常较好。
- Using where：需要 server 层过滤。
- Using filesort：额外排序，需关注。
- Using temporary：使用临时表，需关注。
- Using index condition：索引下推。

## 6. 索引失效常见原因

### 6.1 对索引列使用函数

```sql
SELECT * FROM orders WHERE DATE(create_time) = '2026-07-14';
```

优化：

```sql
SELECT * FROM orders
WHERE create_time >= '2026-07-14 00:00:00'
  AND create_time <  '2026-07-15 00:00:00';
```

### 6.2 隐式类型转换

字段是 varchar，但条件传数字：

```sql
SELECT * FROM user WHERE phone = 13800138000;
```

应该传字符串：

```sql
SELECT * FROM user WHERE phone = '13800138000';
```

### 6.3 like 前缀通配

```sql
SELECT * FROM user WHERE name LIKE '%张%';
```

普通 B+Tree 索引无法有效利用前缀不确定的查询。

### 6.4 联合索引不符合最左前缀

索引：

```sql
idx_a_b_c(a, b, c)
```

可以较好使用：

```sql
WHERE a = ? AND b = ?
```

不一定能有效使用：

```sql
WHERE b = ? AND c = ?
```

### 6.5 范围条件后的列利用受限

索引：

```sql
idx_status_create_type(status, create_time, type)
```

查询：

```sql
WHERE status = 1
  AND create_time > '2026-07-01'
  AND type = 'A'
```

`create_time` 是范围条件，后面的 `type` 是否充分利用要结合执行计划判断。

## 7. 慢 SQL 优化方向

### 7.1 建合适索引

不要只给单列建索引，要结合查询条件设计联合索引。

设计原则：

- 高选择性字段优先。
- 等值条件优先。
- 范围和排序字段放后面。
- 尽量减少回表。
- 避免过多索引影响写入。

### 7.2 使用覆盖索引

覆盖索引指查询字段都在索引中，不需要回表。

示例：

```sql
SELECT id, status, create_time
FROM sync_record
WHERE status = 0
ORDER BY create_time
LIMIT 100;
```

可以考虑索引：

```sql
idx_status_create_id(status, create_time, id)
```

### 7.3 避免深分页

慢查询：

```sql
SELECT * FROM sync_record ORDER BY id LIMIT 100000, 20;
```

优化：

```sql
SELECT * FROM sync_record
WHERE id > 100000
ORDER BY id
LIMIT 20;
```

或者先查主键再回表。

### 7.4 减少返回字段

避免无脑 `SELECT *`。

如果只需要列表字段，就只查列表字段。

大字段如 text、blob、json 要谨慎查询。

### 7.5 拆分大事务

大事务问题：

- 持锁时间长。
- undo log 压力大。
- 回滚成本高。
- 影响并发。

批量更新、批量同步要分批处理。

## 8. 锁等待导致的慢

慢 SQL 不一定是扫描慢，也可能是等锁。

常见原因：

- 长事务未提交。
- 大批量更新。
- 更新条件未命中索引，锁范围扩大。
- 间隙锁导致阻塞。
- 热点行频繁更新。

排查方向：

```sql
SHOW PROCESSLIST;
SHOW ENGINE INNODB STATUS;
```

关注：

- 是否有长时间运行事务。
- 是否有 waiting for lock。
- 哪个 SQL 持有锁。
- 哪个 SQL 被阻塞。

面试表达：

> 如果慢查询日志里 Lock_time 很高，我不会只看索引，而会优先排查锁等待。比如更新条件没有索引，可能扫描并锁住更多记录，导致其他事务阻塞。

## 9. 连接池打满怎么分析

数据库连接池打满可能是结果，不一定是原因。

可能原因：

- SQL 慢导致连接长期占用。
- 事务太长不释放连接。
- 下游数据库压力大。
- 应用并发突然升高。
- 连接池配置太小。
- 代码连接泄露。

排查方式：

- 看活跃连接数和等待线程数。
- 看慢 SQL 是否增加。
- 看接口 RT 是否升高。
- 看是否有长事务。
- 看是否最近流量突增。

处理原则：

> 不能一看到连接池满就盲目加连接数。连接数加大可能把压力继续传给数据库，导致数据库更慢。

## 10. 项目一：中考查询系统排查示例

现象：

```text
成绩开放当天，大量请求 5 秒超时。
Redis 命中率从 90% 降到 40%。
数据库连接池接近打满。
Sentinel 开始限流。
```

排查思路：

1. 先止血：临时收紧限流，保护数据库。
2. 看请求分布：按 IP、准考证号、学校统计。
3. 看是否存在大量非法准考证号。
4. 看 Redis key 是否集中失效或未预热。
5. 看数据库慢 SQL、连接池、锁等待。
6. 看查询 SQL 是否命中索引。
7. 看是否存在深分页或大字段返回。

优化方案：

- 准考证号格式和范围校验。
- 非法请求直接拦截，不进 DB。
- 不存在的数据缓存空值。
- 使用布隆过滤器防穿透。
- 查询结果提前预热。
- 查询接口 QPS 限流。
- 数据库查询方法线程数限流。
- 核心查询 SQL 增加合适联合索引。

面试表达：

> 这个场景里 Redis 命中率突然下降是关键线索，说明大量请求穿透到了数据库。我会先判断是缓存集中失效、缓存未预热，还是大量非法准考证号导致缓存穿透。处理上会先限流止血，再做参数合法性校验、空值缓存或布隆过滤器，同时检查数据库索引和慢 SQL。

## 11. 项目二：数据同步平台排查示例

现象：

```text
Kafka 消费 Lag 上升。
消费者日志显示写目标库耗时变长。
数据库连接池活跃连接接近上限。
慢 SQL 增多。
```

排查思路：

1. 看是所有分区都慢，还是某个分区慢。
2. 看消费者处理耗时分布。
3. 看目标库写入 SQL 是否变慢。
4. 看是否有锁等待或长事务。
5. 看是否批量补偿任务和实时消费同时打库。
6. 看业务主键唯一索引是否冲突频繁。
7. 看目标表数据量增长后索引是否不合理。

优化方案：

- 消费和补偿分开限流。
- 批量写入分批提交。
- 缩短事务时间。
- 写入条件必须命中索引。
- 对同步状态表增加合理索引。
- 慢 SQL 优化后再考虑增加消费者。

面试表达：

> Kafka Lag 上升时不一定是 Kafka 问题，也可能是消费者写库变慢。我要看消费者每条消息处理耗时、目标库慢 SQL、连接池和锁等待。如果数据库已经慢了，盲目增加消费者会进一步加压数据库，应该先解决 SQL 和数据库瓶颈。

## 12. 高频问题

### 12.1 慢 SQL 怎么排查

答法：

> 我会先确认影响范围，是单接口还是全库慢。然后看慢查询日志、APM、数据库监控和连接池指标。定位 SQL 后用 EXPLAIN 看执行计划，重点看 type、key、rows、Extra。再判断是否索引失效、扫描行数过多、排序临时表、锁等待或连接池被占满。

### 12.2 EXPLAIN 主要看哪些字段

答法：

> 主要看 type、key、rows、Extra。type 判断访问类型，key 判断实际使用索引，rows 判断扫描行数，Extra 看是否有 filesort、temporary、Using index 等信息。

### 12.3 为什么有索引还慢

答法：

> 可能是索引选择性差、查询返回行数太多、联合索引顺序不合理、范围条件影响后续列、回表过多、排序无法利用索引、统计信息不准，或者慢的原因不是扫描而是锁等待。

### 12.4 连接池打满怎么办

答法：

> 先看连接为什么不释放，是 SQL 慢、事务长、锁等待、流量突增还是连接泄露。不能直接盲目加连接数，因为可能把压力继续打到数据库。要先定位慢 SQL 和长事务，再决定是否调连接池。

### 12.5 Kafka 消费慢一定是 Kafka 问题吗

答法：

> 不一定。消费慢可能是消费者业务处理慢、数据库慢、下游接口慢、反序列化慢、锁等待或线程池瓶颈。Kafka Lag 上升只是结果，排查要看消费端处理耗时和下游资源。
