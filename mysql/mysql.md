**线上反馈：中考成绩查询接口大量超时，接口平均 RT 从 300ms 升到 5s，数据库连接池接近打满，慢查询日志开始大量出现。 如果让你排查，你会按什么顺序查？不要只说“加索引”，请说完整排查路径。**
> 我会先判断影响范围，是单个成绩查询接口慢，还是整个系统都慢。然后先看应用侧指标，比如 Tomcat 线程、业务线程池、接口 RT、错误率、数据库连接池活跃连接数和等待线程数。
> 这个系统前面有 Redis，所以我会重点看 Redis 命中率是否下降。如果命中率突然下降，要判断是缓存集中失效、缓存未预热，还是大量非法准考证号导致缓存穿透。再按 IP、准考证号、学校维度看流量分布，判断是否被刷接口或热点参数异常。
> 数据库侧我会看 CPU、IO、连接数、慢查询日志、锁等待和长事务。定位具体慢 SQL 后，用 EXPLAIN 看 type、key、rows、Extra，判断是否全表扫描、索引失效、回表过多、filesort、temporary。
> 如果是索引问题，再根据查询条件设计联合索引；如果是锁等待，就看长事务和更新条件是否命中索引；如果是连接池打满，要先解决 SQL 慢和事务不释放，不能一上来盲目加连接数。
> 止血上可以临时收紧限流，对非法准考证号直接拦截，必要时返回查询繁忙，先保护数据库。

**你执行一条 SQL 的 EXPLAIN，看到：- type = ALL - key = NULL- rows = 850000- Extra = Using where; Using filesort 你怎么判断这个 SQL 的问题？接下来怎么优化？**
>答： type=ALL 说明全表扫描，key=NULL 说明没有使用索引，rows=850000 说明预估扫描 85 万行，Using filesort 说明排序没有利用索引，需要额外排序。这条 SQL 的主要问题是过滤和排序都没有被索引有效支撑。
> 优化时我会先看 SQL 的 WHERE 条件和 ORDER BY 字段。如果是类似：
> ```mysql 
> SELECT id, name, score
> FROM exam_score
> WHERE exam_no = ?
> ORDER BY create_time DESC
> ```
> 那我会考虑建立联合索引，比如 (exam_no, create_time)，让过滤和排序尽量都走索引。如果查询字段较少，可以把列表字段放进索引形成覆盖索引，减少回表。
> 同时检查是否存在索引失效，比如对索引列使用函数、隐式类型转换、LIKE '%xxx'、联合索引不符合最左前缀。如果返回数据量本身很大，还要考虑分页、限制返回字段或拆分查询。

**连接池打满？**
>答 我不会直接把连接池从 50 调到 200。连接池打满说明连接被长期占用，可能是 SQL 慢、锁等待、长事务、流量突增或连接泄露导致的。如果直接加连接数，可能只是让更多请求同时打到数据库，把数据库 CPU、IO、锁竞争压得更严重。
> 我会先看连接池监控，比如活跃连接数、等待连接线程数、连接获取耗时；再看数据库慢 SQL、锁等待、长事务和 SHOW PROCESSLIST，确认连接都卡在哪些 SQL 上。
> 如果是慢 SQL，就优化索引和 SQL；如果是锁等待，就找持锁事务并缩短事务范围；如果是流量突增，就临时限流或降级；如果是连接泄露，就排查代码是否没有释放连接。只有确认数据库还有承载能力，并且连接池确实偏小，才会适当调大连接池。

**数据同步平台线上出现 Kafka Lag 持续上升。业务方怀疑 Kafka 出问题了。你看日志发现消费者每条消息处理时间从 200ms 变成 3s，目标库慢 SQL 增多，连接池也接近打满。 你怎么判断问题？怎么处理？**
>答： Kafka Lag 上升不一定是 Kafka 问题。这里消费者单条处理时间从 200ms 变成 3s，同时目标库慢 SQL 增多、连接池接近打满，说明瓶颈大概率在消费者写目标库这一段。
> 我不会先盲目增加消费者，因为目标库已经是瓶颈，加消费者会增加并发写入，可能进一步压垮数据库。
> 排查上先看消费者处理耗时拆分，是查源库慢、业务转换慢，还是写目标库慢。结合慢 SQL 日志和 EXPLAIN，看 type、key、rows、Extra，判断是否全表扫描、索引失效、filesort、锁等待。再看连接池活跃连接、等待线程、长事务和锁等待。
> 处理上先对补偿任务和实时消费做限流，必要时暂停补偿；再优化慢 SQL、补索引、缩短事务、分批提交。如果某些消息一直失败，进入失败表或 DLQ，不要阻塞整个分区。数据库恢复后再逐步提高消费速率。

**数据同步平台里，消费者收到 Kafka 消息后，根据业务主键去源库查询完整业务数据。源库是主从架构。 如果消费者为了减轻主库压力，默认读从库，会有什么风险？你怎么设计？**
>答：> 消费者收到 Kafka 消息后，如果读从库，可能因为源业务数据刚提交，binlog 还没同步或从库还没回放，导致按业务主键查不到数据。这时消费者可能误判为数据不存在或同步失败，进入失败表，甚至触发不必要的补偿。
> 我的设计是核心同步链路读主库，尤其是消费者查询源业务数据、补偿任务扫描同步状态、写后立刻查状态这些场景都读主库。历史列表、报表、管理端非实时查询可以读从库。
> 如果必须读从库，要做主从延迟监控，延迟超过阈值时切主库；补偿任务也要加时间窗口，比如只扫描 5 分钟前仍未成功的数据，避免刚写入的数据因为延迟被误补偿。同时消费者侧还要有幂等和补偿机制兜底。

**你简单说一下 MySQL 主从复制的流程，以及为什么会产生主从延迟。**
>答： > MySQL 主从复制流程是：主库事务提交后写入 binlog；从库的 IO 线程连接主库，拉取 binlog 写入本地 relay log（中继日志）；从库的 SQL 线程再读取 relay log 并回放 SQL 或行变更，最终让从库数据追上主库。
> 主从延迟产生的本质是主库产生 binlog 的速度超过从库拉取和回放的速度。常见原因包括主库写入突增、大事务、DDL、从库机器性能差、网络延迟、从库 SQL 线程回放慢、表缺少主键或索引、从库同时跑大查询或报表任务。

**半同步复制？**
>答： 半同步复制不能彻底解决主从延迟和数据一致性问题。它主要解决的是主库宕机时数据丢失风险，通常要求主库提交时至少等待一个从库确认收到 binlog 后再返回。
> 但“收到 binlog”不等于“已经回放完成”，所以应用读从库时仍然可能读到旧数据，主从延迟仍然存在。如果从库收到日志后还没回放，或者后续故障，也可能造成短时间不一致。
> 所以业务上不能因为用了半同步就随便读从库。写后读、状态判断、补偿扫描仍然要读主库或做延迟判断，同时通过幂等、状态机、补偿机制保证最终一致。
