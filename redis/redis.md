**中考成绩查询系统里，成绩开放当天，有大量请求携带伪造的准考证号查询。Redis 查不到，数据库也查不到，导致数据库压力快速升高。 你会怎么判断这是缓存穿透？怎么治理？**
>答： 我会先看 Redis 命中率是否明显下降，同时看 DB 查询结果中空结果比例是否升高，再按准考证号、IP、学校维度统计请求。如果大量准考证号不符合格式或不在合法号段内，并且 Redis 和 DB 都查不到，就是典型缓存穿透。
> 治理上第一步是在进入缓存和数据库前做准考证号格式和范围校验，非法请求直接返回。第二，对 DB 确认不存在的数据缓存空值，设置较短 TTL，避免相同非法号反复打库。第三，如果合法准考证号集合稳定，可以用布隆过滤器提前判断是否存在。第四，在
> Gateway 或 Sentinel 层按 IP、接口、准考证号做限流，防止恶意请求压垮系统。


**同样是中考查询系统，某个热点 Key，比如 exam:query:config 或某个热门学校统计 Key 突然过期，大量请求同时打到数据库。 这是缓存穿透、击穿还是雪崩？你怎么处理？**
> 答：这是缓存击穿，特点是某个热点 Key 过期，大量并发同时回源 DB。处理上可以用互斥锁，只允许一个线程查 DB 并重建缓存，其他线程短暂等待后再读缓存，或者直接返回旧值/降级结果，不能无限阻塞。
> 对查询配置、公告这类热点 Key，我更倾向于逻辑过期或永不过期加异步刷新，请求发现逻辑过期时先返回旧值，由后台线程刷新缓存。读多写少的热点配置还可以加本地缓存或多副本 Key，降低 Redis 单点压力。TTL 也要加随机值，避免集中失效。

**如果大量成绩缓存 Key 在同一时间失效，Redis 命中率从 90% 掉到 30%，数据库连接池快速打满。 这是缓存雪崩。你会怎么提前预防？线上已经发生时怎么止血？**
>答 > 缓存雪崩是大量 Key 同一时间失效，或者 Redis 整体不可用，导致请求集中打到数据库。
> 预防上，第一，缓存 TTL 加随机值，避免同一批 Key 同时过期；第二，成绩开放查询前做缓存预热，把高频查询数据提前加载到 Redis；第三，热点配置类数据可以本地缓存或逻辑过期；第四，Redis 本身要做高可用；第五，接口层要有 Sentinel/Gateway 限
> 流。 如果线上已经发生，先止血：临时收紧限流，保护数据库连接池；对非核心接口降级；对于非法准考证号直接拦截；必要时返回“查询繁忙，请稍后再试”。同时启动缓存回填或分批预热，避免所有请求直接回源 DB。等 DB 压力下降后，再逐步放开限流。

**Redis Cluster 已经做了分片。有人说：“热点 Key 不用管，Redis Cluster 会自动把压力分散到不同节点。” 你怎么看？为什么？怎么治理热点 Key？**
>答： Redis Cluster 能分散不同 Key，但同一个 Key 只能落到一个 slot，最终由一个节点处理，所以热点 Key 仍然会造成单节点 CPU、网络、RT 升高。
> 治理上，对于读多写少的配置类热点，可以用本地缓存加异步通知刷新；对于内容相同的热点数据，可以拆成多个副本 Key，读取时随机访问；对于热点 Key 过期问题，可以使用逻辑过期或永不过期加异步刷新；缓存重建时用互斥锁，避免大量请求同时回源。发现
> 上可以通过应用访问统计、Redis 节点负载倾斜、慢日志和 hotkeys 分析。

**如果有人把全县 5.5 万考生的成绩列表缓存成一个 Redis Key，比如 exam:all:scores，你怎么看？有什么风险？怎么改？**
>答：> 我不建议把全县 5.5 万考生成绩缓存成一个 exam:all:scores 大 Key。风险是单次读取网络报文大、序列化反序列化慢、Redis 单线程执行命令可能阻塞其他请求；删除时如果用 DEL 会阻塞，集群迁移 slot 时也会很慢，还会造成内存倾斜。
> 更合理的是按查询模式拆。中考查询主要按准考证号查，那就按 exam:score:{ticketNo} 缓存单个考生成绩；学校统计可以按 exam:school:{schoolId}:summary 缓存摘要；列表类数据按页缓存，比如 exam:school:{schoolId}:page:{pageNo}。
> 如果已经存在大 Key，要先识别大小，低峰期迁移和拆分；删除时用 UNLINK，避免直接 DEL 阻塞 Redis。

**你们更新一条成绩数据或同步状态时，Redis 里也缓存了这条数据。 你会选择：- 先删缓存，再更新数据库？- 先更新数据库，再删缓存？ -还是直接更新缓存？ 你怎么选？为什么？如果删除缓存失败怎么办？**
>答： > 我一般选择先更新数据库，再删除缓存，不直接更新缓存。因为缓存通常是派生数据，结构可能和数据库不完全一致，直接更新容易漏字段或并发覆盖。
> 如果先删缓存再更新数据库，可能出现并发读：缓存被删后，另一个线程读数据库旧值并写回缓存，随后数据库才更新成新值，最终 Redis 里反而是旧值。
> 所以更常用的是更新数据库成功后删除缓存。这样即使缓存删除失败，也可以通过删除重试、MQ 异步补偿、binlog 监听和 TTL 兜底保证最终一致。对同步状态这类重要数据，我不会只靠 TTL，会把删除失败记录下来重试，或者发 MQ 做异步删除。

**数据同步平台里，有人建议用 Redis SETNX sync:{bizId} 来做消费幂等。只要 SETNX 成功就处理，失败就认为重复消息。 你怎么看？Redis 能不能作为幂等的最终依据？为什么？你会怎么设计？**
>答：> Redis 可以做幂等的前置拦截，但不能作为最终依据。因为 Redis Key 可能过期、被淘汰，Redis 宕机或主从切换也可能丢数据；而且 SETNX 成功后，如果业务处理失败或服务宕机，Redis 里可能留下 processing 状态，不能代表数据库真的处理成功。
> 我的设计是 Redis 用来降低重复请求压力，比如 SETNX sync:{bizId} 短期拦截重复消费；但最终幂等要靠数据库业务唯一键、唯一索引和状态机。消费者处理时根据业务主键判断目标表是否已存在，存在则更新或跳过，不存在则插入；同步记录表维护 pending、
> processing、success、failed 状态，并配合最大重试次数和补偿任务。
> 这样即使 Redis 丢失或过期，数据库仍然能保证不会重复写脏数据。

**中考成绩查询系统高峰期 Redis 宕机了。 如果所有请求直接查数据库，数据库可能马上被打挂。 你会怎么处理？请说线上止血和后续优化。**
>答：> Redis 宕机时不能让所有请求直接打数据库。线上先止血：Gateway/Sentinel 收紧限流，保护数据库连接池；对非核心接口直接降级；查询接口可以只放很小比例请求查 DB，其余返回“查询繁忙，请稍后再试”；对非法准考证号继续做格式和范围校验，不能进入
> DB；查询开放时间、公告这类配置可以用本地缓存兜底。
> 同时通知运维恢复 Redis，恢复后不要一次性全量回源，要分批预热热点数据，再逐步放开限流。
> 后续优化上，Redis 要做高可用，比如主从、哨兵或 Cluster；关键热点配置做本地缓存；成绩缓存 TTL 加随机值；查询前做缓存预热；并补充 Redis 可用性、命中率、慢命令、内存、连接数等监控告警。
> Redis 是性能加速层，不应该成为系统正确性的唯一依赖；但高峰查询场景下 Redis 宕机会严重影响可用性，所以必须有限流降级预案。

**你在项目里怎么使用 Redis？遇到高并发查询和缓存一致性问题怎么处理？**
>答：Redis 在我们项目里主要承担三类职责：第一是缓存，比如中考查询系统中的成绩查询结果、查询开放时间、学校字典、系统公告；第二是限流和状态类数据，比如查询状态、短期统计；第三是分布式锁或幂等前置拦截，比如数据同步平台里防止同一批次补偿任务
> 重复执行。
> 在中考查询系统里，Redis 的核心作用是保护数据库。成绩开放当天访问量会集中爆发，所以查询流程不是直接查 DB，而是先校验准考证号格式和合法范围，再查 Redis，命中直接返回，未命中再查数据库并写入缓存。对于不存在的数据，会缓存短 TTL 空值，防
> 止缓存穿透；对成绩结果设置随机 TTL，避免大量 Key 同时过期造成雪崩；对查询开放时间、公告这类热点 Key，可以做本地缓存或逻辑过期异步刷新，避免热点 Key 过期后大量请求打到数据库。
> 对大 Key 和热点 Key，我会特别注意。比如不能把全县 5.5 万考生成绩放到一个 Redis Key 里，这会造成网络传输大、Redis 单线程阻塞、删除和迁移风险。更合理的是按准考证号缓存单个成绩，学校统计按学校维度缓存，列表按页缓存。热点 Key 即使在
> Redis Cluster 下也只会落到一个 slot，所以需要本地缓存、多副本 Key 或逻辑过期来分散压力。
> 缓存一致性方面，我一般采用 Cache Aside 模式：读的时候先查缓存，未命中查数据库并回写；写的时候先更新数据库，再删除缓存，不直接更新缓存。因为先删缓存再更新数据库，在并发读场景下可能把旧值重新写入缓存；更新数据库后删除缓存失败，则通过重
> 试、MQ 补偿、binlog 监听或 TTL 兜底保证最终一致。
> 在数据同步平台里，Redis 可以做同步开关、短期状态缓存、失败统计、分布式锁和幂等前置拦截，但不能作为最终一致性的依据。比如消费幂等不能只靠 Redis SETNX，因为 Key 可能过期、淘汰或 Redis 故障，最终还是余返回查询繁忙。同时利用本地缓存兜底
> 配置类数据，等 Redis 恢复后分批预热，再逐步放开流量。
