## 1. SETNX 实现基础分布式锁

### 基本命令

```bash
SET lock_key unique_value NX EX 10
```

- **NX**：key 不存在才设置成功（互斥的核心）
- **EX 10**：设置 10 秒过期时间（防止死锁）
- **unique_value**：通常用 UUID 或机器标识，**不能是固定值**（解锁时要校验持有者身份，下面会讲原因）

### 为什么不能用 SETNX + EXPIRE 两条命令

早期很多教程这样写：

```bash
SETNX lock_key 1
EXPIRE lock_key 10
```

**问题**：这是两条独立命令，**不是原子操作**。如果 `SETNX` 执行成功后，进程在执行 `EXPIRE` 之前崩溃（被kill、宕机等），这个锁就会变成**永久锁**，没有过期时间，谁也释放不了。

所以必须用 `SET key value NX EX seconds` 这种**单命令原子写法**（Redis 2.6.12+ 支持）。

### 释放锁

```bash
DEL lock_key
```

但直接 DEL 也有问题——见下一节。

## 2. 存在的问题

### 2.1 超时问题（业务执行时间 > 锁过期时间）

```
T0:  客户端A加锁,设置10秒过期
T1:  客户端A开始执行业务逻辑(假设要15秒)
T10: 锁自动过期被释放
T10+:客户端B加锁成功,开始执行自己的业务
T15: 客户端A业务执行完毕,执行DEL释放锁
     → 但此时锁是客户端B的!A把B的锁删了!
```

**后果**：A、B 同时处于"持锁"状态执行业务，分布式锁的互斥性被破坏。

### 2.2 误删问题（解锁时没有校验持有者）

即使不考虑超时，如果解锁逻辑写成：

```bash
DEL lock_key   # 不管是谁的锁,直接删
```

任何客户端都能删掉别人持有的锁。正确做法：**只有锁的持有者才能释放自己加的锁**，常见解法是用 Lua 脚本保证"校验+删除"的原子性：

```lua
-- 释放锁的Lua脚本
if redis.call("GET", KEYS[1]) == ARGV[1] then
    return redis.call("DEL", KEYS[1])
else
    return 0
end
```

`ARGV[1]` 传入自己当初加锁时设置的 `unique_value`，只有匹配才删除——这就是为什么加锁时 value 不能是固定值的原因。

### 2.3 不可重入问题

**场景**：同一个线程内，方法A已经持有锁，内部又递归/调用了另一个也需要同一把锁的方法B。

```java
lock();    // 方法A加锁成功
methodB(); // 内部又调用 lock() 尝试加同一把锁
           // 但 SETNX 发现key已存在 → 加锁失败!
           // 自己把自己锁死了
unlock();
```

普通的 SETNX 实现**不知道"这把锁是不是自己已经持有的"**，导致同线程重复加锁会失败，这在递归调用、同一事务内多次操作同一资源的场景下是个硬伤。

## 3. Redisson 实现（看门狗机制）

Redisson 是 Java 生态最常用的 Redis 客户端，内置了一套完整的分布式锁实现，针对上述三个问题都有解法。

### 3.1 解决"误删"——自动用 unique_value + Lua

Redisson 加锁时，value 实际存的是 `UUID:线程ID`，解锁时同样靠 Lua 脚本校验身份再删除，思路与上面手写的一致，只是 Redisson 帮忙封装好了。

### 3.2 解决"不可重入"——用 Hash 结构 + 计数器

Redisson 的锁底层**不是简单的 String**，而是用 **Hash** 结构存储：

```
key:   lock_key
field: UUID:threadId
value: 重入次数(计数器)
```

加锁的 Lua 逻辑（简化版）：

```lua
if (redis.call('exists', KEYS[1]) == 0) then
    -- key不存在,直接加锁,计数器=1
    redis.call('hset', KEYS[1], ARGV[2], 1)
    redis.call('pexpire', KEYS[1], ARGV[1])
    return nil
end
if (redis.call('hexists', KEYS[1], ARGV[2]) == 1) then
    -- 是自己已经持有的锁,计数器+1(重入)
    redis.call('hincrby', KEYS[1], ARGV[2], 1)
    redis.call('pexpire', KEYS[1], ARGV[1])
    return nil
end
return redis.call('pttl', KEYS[1]) -- 锁被别人持有,返回剩余时间
```

解锁时计数器 **-1**，减到 0 才真正 `DEL` 删除锁——这样同一线程可以重复加锁、重复解锁，只有最外层的 unlock 才真正释放。

### 3.3 解决"超时"——看门狗（Watchdog）机制

这是 Redisson 最核心的设计：

**原理**：

1. 客户端加锁成功后，Redisson 在后台启动一个**守护线程（看门狗）**
2. 看门狗每隔 **锁过期时间的 1/3**（默认锁30秒过期，则每10秒检查一次），检查客户端是否还持有这把锁、业务是否还在执行
3. 如果业务还没执行完，看门狗就调用 `pexpire` **自动给锁"续命"**，重新设置为30秒过期
4. 业务执行完毕、正常调用 `unlock()` 后，看门狗线程才会停止续期

```
T0:  加锁成功,默认30秒过期,看门狗启动
T10: 看门狗检查 → 业务还在跑 → 续期到30秒(剩余变成T10+30)
T20: 看门狗检查 → 业务还在跑 → 续期到30秒(剩余变成T20+30)
T25: 业务执行完毕,调用unlock() → 看门狗停止,锁被删除
```

**效果**：只要客户端还活着、业务还在正常执行，锁就不会因为"业务时间超过预设过期时间"而被误释放。**只有客户端进程真的挂了（看门狗线程也跟着死了）**，锁才会在原定时间后自然过期，避免死锁。

> **注意**：看门狗默认机制基于 `lockWatchdogTimeout`（默认30秒）。如果加锁时手动指定了过期时间（`lock(10, TimeUnit.SECONDS)`），Redisson 就**不会**启动看门狗自动续期，到点就是到点——这是使用时要特别注意的一个坑。

## 4. RedLock 算法（多节点）

### 4.1 要解决什么问题

前面讨论的都是**单个 Redis 节点**（或主从架构，本质仍依赖一个主节点）加锁。如果该节点宕机、或主从间数据还没同步完就发生了故障转移，可能出现：

```
T0: 客户端A在Master上加锁成功
T1: Master宕机,数据还没来得及同步给Slave(异步复制有延迟)
T2: 哨兵把Slave提升为新Master → 新Master上根本没有这把锁的记录!
T3: 客户端B在新Master上加锁 → 成功!
    → A和B同时认为自己持有锁
```

这就是**单点（或主从）架构在故障转移场景下的锁安全性问题**。

### 4.2 RedLock 核心思路

不依赖单个 Redis 实例，而是部署**多个独立的 Redis 主节点**（官方推荐 **5个**，它们之间没有主从关系，完全独立）。加锁时：

1. 客户端依次**向所有N个节点**尝试加锁（用同样的key、同样的value、同样的过期时间）
2. 只要在**多数节点**（N/2+1，比如5个节点中至少3个）上加锁成功，**且总耗时小于锁的过期时间**，就认为整体加锁成功
3. 加锁成功后，锁的有效时间 = 原设置时间 - 已消耗的加锁耗时（留出实际可用窗口）
4. 释放锁时，向**所有节点**发送解锁请求（不管之前是否在该节点加锁成功过，保证清干净）

### 4.3 为什么"多数节点成功"就算成功

这是经典的**分布式系统容错思路**（类似 Raft/Paxos 的多数派）：

- 只要节点总数为 N，最多容忍 **(N-1)/2** 个节点同时故障/不可用
- 比如5个节点，挂2个还能凑够3个多数派；只要不超过这个容错边界，锁的安全性就有保障
- 不同客户端不可能同时在"多数节点"上都拿到同一把锁——反证：如果A拿到了3个节点的锁，B想拿到锁也至少要拿到3个节点，但5个节点里必然有重叠的至少1个节点，意味着这个节点同时把锁给了A和B，违反了单节点SETNX的互斥性，矛盾

### 4.4 RedLock 的争议

值得了解的是，RedLock 并非没有争议。分布式系统专家 **Martin Kleppmann** 写过一篇著名文章质疑 RedLock 的安全性，核心争论点：

- RedLock 依赖**系统时钟**（要求各节点时钟相对同步、且加锁耗时计算准确），**时钟漂移、GC停顿、网络延迟**等都可能让"过期时间"的判断失真，导致锁在业务还没执行完时就被认为过期
- Redis 作者 antirez 对此做了回应，认为在实际工程场景下风险可控

### 4.5 实践建议

| 场景 | 建议 |
|------|------|
| 业务对锁安全性要求**没那么极致**（容忍极小概率并发问题） | 单 Redis 节点 + 看门狗（Redisson模式），性能更好、复杂度更低 |
| 金融级、对一致性要求极高的场景 | 不要只依赖 Redis 锁，考虑用 **ZooKeeper**（基于强一致的ZAB协议）或数据库锁兜底 |

## 5. 演进关系总结

```
SETNX(单命令)
   │  问题:超时被误删
   ▼
SET key value NX EX(原子加锁) + Lua脚本校验删除
   │  问题:业务超时 / 不可重入
   ▼
Redisson(Hash计数器解决重入 + 看门狗自动续期解决超时)
   │  问题:单点/主从故障转移下的锁安全性
   ▼
RedLock(多个独立Master,多数派加锁,容忍部分节点故障)
   │  争议:依赖时钟假设,有学者质疑
   ▼
极致一致性场景 → 考虑ZooKeeper等强一致组件兜底
```

### 核心要点回顾

| 问题 | 解决方案 |
|------|---------|
| 加锁非原子（SETNX+EXPIRE分离） | 用 `SET key value NX EX` 单命令 |
| 误删别人的锁 | value 用唯一标识 + Lua脚本校验后再删 |
| 业务超时锁被提前释放 | 看门狗机制自动续期 |
| 同线程不可重入 | Hash结构 + 计数器记录重入次数 |
| 单点/主从故障转移锁失效 | RedLock多数派算法（多个独立Master） |
