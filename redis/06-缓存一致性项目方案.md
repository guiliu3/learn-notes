# 06-缓存一致性项目方案

## 1. 面试先给结论

缓存一致性不是追求 Redis 和数据库任何时刻都完全一致，而是根据业务场景选择强一致、最终一致或可短暂不一致的方案。

面试表达可以这样说：

> 我理解缓存一致性的核心不是背“先删缓存还是先更新数据库”，而是先判断业务对一致性的要求。像成绩查询、公告、配置这类读多写少场景，可以接受短时间最终一致；像支付状态、同步状态、权限变更这类场景，要更谨慎，必要时读主库或不依赖缓存做最终判断。常规方案是更新数据库后删除缓存，通过 TTL、重试、消息补偿、延迟双删和幂等设计降低不一致窗口。

## 2. 缓存一致性为什么难

因为数据库和 Redis 是两个系统。

常见操作：

```text
写数据库
删缓存
读缓存
回源数据库
重建缓存
```

任意步骤都可能失败：

- 数据库更新成功，缓存删除失败。
- 缓存删除成功，数据库更新失败。
- 删除缓存后，旧请求回源并写入旧值。
- 主从延迟导致回源读到旧数据。
- 并发更新导致缓存被覆盖。

所以缓存一致性本质是分布式一致性问题。

## 3. 常见缓存策略

### 3.1 Cache Aside

最常见模式。

读流程：

```text
先读 Redis
命中则返回
未命中则读 DB
写 Redis
返回结果
```

写流程：

```text
更新 DB
删除 Redis
```

为什么不是更新缓存：

- 缓存结构可能和 DB 不一致。
- 更新缓存容易漏字段。
- 并发更新容易覆盖。
- 很多数据写后不一定会被读。

面试表达：

> 我更常用 Cache Aside，读时先查缓存，未命中查数据库并回写缓存；写时先更新数据库，再删除缓存。删除缓存比更新缓存更简单，也能避免复杂对象更新不完整的问题。

## 4. 先更新数据库还是先删缓存

### 4.1 先删缓存，再更新数据库

风险：

```text
线程 A 删除缓存
线程 B 查询缓存未命中
线程 B 读 DB 旧值
线程 B 写入旧缓存
线程 A 更新 DB 新值
```

结果：

```text
DB 是新值，Redis 是旧值
```

### 4.2 先更新数据库，再删缓存

风险：

```text
线程 A 更新 DB 成功
线程 A 删除缓存失败
```

结果：

```text
DB 是新值，Redis 还是旧值
```

但是这个方案通常更常用，因为可以通过：

- 删除重试。
- MQ 补偿。
- binlog 监听。
- TTL 兜底。

来修复。

面试表达：

> 一般我会选择先更新数据库，再删除缓存。因为先删缓存再更新数据库，在并发读场景下更容易把旧值重新写回缓存。更新 DB 后删缓存也有失败风险，所以需要删除重试、MQ 补偿或 TTL 兜底。

## 5. 删除缓存失败怎么办

常见方案：

### 5.1 本地重试

删除失败后短暂重试。

适合：

- 偶发网络抖动。
- 对可靠性要求一般。

缺点：

- 应用重启可能丢失重试任务。

### 5.2 MQ 异步重试

数据库更新成功后，发送缓存删除消息。

流程：

```text
1. 更新 DB。
2. 发送缓存删除消息。
3. 消费者删除 Redis。
4. 删除失败进入重试或 DLQ。
```

适合：

- 重要业务。
- 需要可追踪、可补偿。

### 5.3 监听 binlog

通过 Canal 等工具监听数据库 binlog，异步删除或更新缓存。

优点：

- 业务代码侵入小。

缺点：

- 链路更长。
- 需要维护同步组件。
- 有延迟。

### 5.4 TTL 兜底

缓存设置过期时间，即使删除失败，也会最终过期。

注意：

> TTL 是兜底，不是强一致保证。

## 6. 延迟双删

延迟双删流程：

```text
1. 删除缓存。
2. 更新数据库。
3. 延迟一段时间后再次删除缓存。
```

目的：

- 降低并发读把旧值写回缓存的概率。

问题：

- 延迟时间不好确定。
- 增加实现复杂度。
- 不是强一致。

面试表达：

> 延迟双删可以降低并发场景下旧缓存回写的问题，但不是万能方案。延迟时间依赖业务读写耗时和主从延迟，生产上我更倾向于更新 DB 后删缓存，并结合 MQ 重试和 TTL 兜底。

## 7. 缓存穿透、击穿、雪崩

### 7.1 缓存穿透

查询的数据不存在，缓存和数据库都没有。

风险：

- 大量非法请求绕过缓存打到 DB。

方案：

- 参数校验。
- 缓存空值。
- 布隆过滤器。
- 接口限流。

中考查询系统：

> 大量伪造准考证号查询，如果不做合法性校验，会造成缓存穿透。

### 7.2 缓存击穿

热点 Key 过期，大量请求同时回源数据库。

方案：

- 互斥锁重建缓存。
- 逻辑过期异步刷新。
- 热点 Key 不设置短 TTL。
- 本地缓存。

### 7.3 缓存雪崩

大量 Key 同时失效，或者 Redis 整体不可用。

方案：

- TTL 加随机值。
- 缓存预热。
- 多级缓存。
- Redis 高可用。
- 限流降级。

## 8. 读写并发下的数据不一致

典型场景：

```text
线程 A 更新 DB 后准备删缓存
线程 B 读取缓存旧值
线程 A 删除缓存
线程 C 再读 DB 新值并写缓存
```

短时间读到旧值是可能存在的。

判断是否可接受：

- 成绩查询结果：发布后基本不变，可以接受短暂一致性窗口，但发布前要预热准确。
- 权限变更：通常希望立即生效，缓存 TTL 要短或主动删除。
- 同步状态：不能完全依赖缓存，最终以 DB 为准。
- 支付状态：强一致场景，谨慎用缓存做判断。

## 9. 中考查询系统缓存方案

### 9.1 缓存对象

适合缓存：

- 准考证号查询结果。
- 查询开放时间。
- 学校信息。
- 区县字典。
- 系统公告。

不适合缓存或需谨慎：

- 高频变更状态。
- 需要严格实时一致的数据。

### 9.2 查询流程

```text
1. 校验准考证号格式和范围。
2. 查询 Redis。
3. 命中则返回。
4. 未命中查询 DB。
5. DB 有结果，写入 Redis，TTL 加随机值。
6. DB 无结果，缓存短 TTL 空值。
```

### 9.3 高峰保护

措施：

- 查询开放前缓存预热。
- TTL 增加随机值。
- 非法准考证号拦截。
- 不存在数据缓存空值。
- 热点配置本地缓存。
- Sentinel 限流。
- Redis 异常时降级提示。

面试表达：

> 中考查询系统读多写少，适合用 Redis 缓存查询结果。查询前先校验准考证号合法性，再查 Redis，未命中才查 DB。不存在的数据缓存短 TTL 空值，防止穿透；成绩结果 TTL 加随机值，避免雪崩；查询开放前做缓存预热，热点公告和开放时间可以做本地缓存。

## 10. 数据同步平台缓存方案

### 10.1 能缓存什么

适合缓存：

- 同步开关。
- 业务字典。
- 短期状态展示。
- 失败统计。
- 限流计数。

不适合作为唯一依据：

- 最终同步状态。
- 幂等最终判断。
- 补偿扫描条件。

### 10.2 同步状态一致性

原则：

> 同步状态以数据库为准，Redis 只能做加速展示或短期缓存。

原因：

- Kafka 消费可能重复。
- Redis 可能过期或丢失。
- 删除缓存可能失败。
- 补偿任务需要可靠状态。

### 10.3 幂等设计

Redis 可以做提前拦截：

```text
SETNX sync:biz:{bizId} processing EX 300
```

但最终幂等要靠：

- 数据库唯一索引。
- 业务主键。
- 状态机。
- 乐观锁。

面试表达：

> 数据同步平台里，Redis 可以做同步开关、短期状态缓存、失败统计和幂等前置拦截，但最终状态不能只依赖 Redis。比如重复消费时，Redis 可能过期或丢失，所以最终还是要靠数据库业务主键、唯一索引和状态机保证幂等。

## 11. Redis 宕机怎么办

中考查询系统：

- 查询接口限流。
- 直接查 DB 需要严格控制并发。
- 返回“查询繁忙”。
- 使用本地缓存兜底部分配置。
- 等 Redis 恢复后逐步回源预热。

数据同步平台：

- 核心同步链路不能依赖 Redis 才能正确。
- Redis 宕机时关闭非核心缓存。
- 幂等最终以 DB 唯一索引为准。
- 分布式锁失败时避免执行高风险批量任务。

面试表达：

> Redis 宕机时不能让所有请求直接打 DB，否则会造成雪崩。中考查询系统要限流降级，必要时返回查询繁忙；数据同步平台的正确性不能依赖 Redis，幂等最终要靠数据库唯一索引，Redis 只是优化性能。

## 12. 缓存一致性和主从延迟

如果回源 DB 读的是从库，还要考虑主从延迟。

风险：

```text
主库更新成功
删除缓存
请求未命中缓存
回源读从库旧值
旧值写回 Redis
```

处理：

- 写后短时间读主库。
- 强一致业务回源读主库。
- 监听主从延迟，延迟高时切主库。
- TTL 兜底。

数据同步平台尤其要注意：

> 同步状态更新后，如果缓存删除了，但回源读从库旧状态，又把旧状态写回 Redis，会导致管理端看到错误状态。

## 13. 高频问题

### 13.1 缓存和数据库如何保证一致性

答法：

> 常用 Cache Aside，读缓存未命中查 DB 并回写；写时先更新 DB，再删除缓存。删除失败通过重试、MQ 补偿、binlog 监听和 TTL 兜底保证最终一致。

### 13.2 为什么不是先删缓存再更新 DB

答法：

> 先删缓存再更新 DB，在并发读场景下，其他线程可能读到 DB 旧值并写回缓存，导致 DB 更新后缓存仍是旧值。

### 13.3 删除缓存失败怎么办

答法：

> 可以本地重试，也可以发送 MQ 异步删除，失败进入重试或 DLQ；还可以通过 binlog 监听异步处理，TTL 作为最终兜底。

### 13.4 缓存穿透怎么处理

答法：

> 参数合法性校验、缓存空值、布隆过滤器和限流。比如中考查询系统要先校验准考证号格式和范围，非法请求不进入 DB。

### 13.5 Redis 能不能作为幂等的最终依据

答法：

> 不建议。Redis 可以做前置拦截，但它可能过期、丢失或被淘汰。最终幂等应该依赖数据库唯一索引、业务主键和状态机。
