1. 哈希槽（16384个槽）
2. 数据分片原理

## 1. 哈希槽（16384个槽）

### 1.1 为什么是 16384

Redis Cluster 把整个数据空间划分成固定的 **16384（2^14）个槽（slot）**，每个 key 必属于其中一个槽。这个数字不是随便定的，作者权衡过：

- 槽位数太小（比如100以内）：节点一多,每个节点分到的槽位太粗,负载不够均衡
- 槽位数太大（比如65536，2字节能表示的最大值）：心跳包里要携带每个节点的槽位**位图**（bitmap）,16384位 = 2KB,如果用65536则要8KB,在大规模集群下心跳包开销会显著增大
- 16384 是作者认为的甜点：**集群规模通常不会超过1000个节点**，槽位粒度够细、心跳开销也可控

### 1.2 槽位的本质

槽位是一个**逻辑分区**，本身不存数据,只是数据归属的"标签"。集群里每个负责数据的主节点会管理一段连续或不连续的槽位区间，例如3主节点的典型分布：

```
Master-A: 0     ~ 5460   (5461个槽)
Master-B: 5461  ~ 10922  (5462个槽)
Master-C: 10923 ~ 16383  (5461个槽)
```

### 1.3 槽位状态

槽位在迁移过程中会有特殊标记（详见第3节扩容缩容）：

| 状态 | 说明 |
|------|------|
| 正常 | 槽位完全归属某一个节点，可直接读写 |
| **MIGRATING** | 槽位正在从本节点迁出 |
| **IMPORTING** | 槽位正在迁入本节点 |

## 2. 数据分片原理

### 2.1 key → 槽位的映射算法

```
slot = CRC16(key) % 16384
```

每个写入/读取的 key，都先经过 CRC16 哈希算法计算出一个数值，再对 16384 取模，得到该 key 应该落在哪个槽位。

### 2.2 为什么不直接用一致性哈希或简单取模到节点

| 方式 | 问题 |
|------|------|
| **简单哈希取模到节点**（`hash(key) % 节点数`） | 节点数变化时（加/减节点），几乎所有 key 的归属节点都会变,造成大规模数据迁移 |
| **一致性哈希** | 改善了节点变化时的迁移量,但节点数少时容易数据倾斜,且没有"槽位"这种清晰、可管理的迁移单元 |
| **Redis 的槽位方案**（key → 槽位 → 节点，两层映射） | 节点变化时,只需迁移**槽位**(槲位归属可灵活调整),不用重新计算所有 key,迁移成本可控、过程平滑、且每个槲位的迁移状态可追踪 |

### 2.3 hash tag：让相关 key 落到同一槽位

默认情况下，Cluster 不允许跨槽位的多 key 操作（比如不能 `MGET key1 key2` 如果两者不在同一槽位）。如果业务需要把相关数据强制分到一起，可以用 `{}` 语法：

```
user:{1000}:profile
user:{1000}:orders
user:{1000}:cart
```

计算槽位时只取 `{}` 内的内容（这里是 `1000`）做 CRC16，因此这三个 key **必定落在同一槲位**，可以一起执行 `MGET`、事务（`MULTI`）、Lua 脚本等需要多key操作的逻辑。

### 2.4 客户端如何找到正确节点

1. 客户端可连接集群中**任意节点**发起请求
2. 节点检查该 key 计算出的槽位是否归自己管：
    - **是** → 直接处理并返回结果
    - **不是** → 返回 `-MOVED <slot> <ip>:<port>`，告知正确节点地址
3. 主流客户端 SDK（Jedis、Lettuce 等）会在本地**缓存槽位→节点的映射表**，自动处理重定向并刷新缓存，业务代码无需关心这层细节

> 槲位迁移过程中,还存在 `-ASK` 临时重定向（区别于 MOVED,不会更新本地缓存),专门处理"迁移中"的请求。

## 3. 集群扩容 / 缩容

### 3.1 整体思路

加节点或减节点，本质上都是**槲位的重新分配**——把一部分槲位（及其对应的数据）从旧节点迁移到新节点，或者反过来。整个过程**不需要停机**，是在线完成的。

### 3.2 扩容流程（新增主节点）

**步骤一：新节点加入集群**
```bash
redis-cli --cluster add-node <新节点ip:port> <已有节点ip:port>
```
新节点通过 `CLUSTER MEET` 与已有节点建立连接,并通过 Gossip 协议被集群中所有节点感知到。此时新节点**还没有分配任何槲位**，不负责任何数据。

**步骤二：分配槲位（reshard）**
```bash
redis-cli --cluster reshard <任意节点ip:port>
```
为新节点从其他节点那里"匀"一部分槲位过来。具体到单个槲位的迁移过程：

1. 目标（新）节点标记该槲位为 **IMPORTING**
2. 源节点标记该槲位为 **MIGRATING**
3. 源节点通过 `MIGRATE` 命令**逐个 key** 迁移数据到目标节点
4. 迁移期间该槲位仍可正常读写，访问到尚未迁移完的 key 会触发 `-ASK` 重定向到新节点
5. 槲位内所有 key 迁移完毕后，**广播该槲位的新归属**（通过 Gossip 协议扩散），所有节点更新自己的槲位映射表

**步骤三（可选）：给新主节点挂从节点**
为保证新节点也有高可用能力，再给它配置一个或多个 slave。

### 3.3 缩容流程（下线一个主节点）

与扩容相反，缩容是先**迁出**槲位，再下线节点：

**步骤一：把待下线节点的槲位迁移到其他节点**
```bash
redis-cli --cluster reshard <任意节点ip:port>
# 指定从待下线节点迁出全部槲位,迁入到保留的节点
```
迁移机制与扩容时完全一致（IMPORTING / MIGRATING / MIGRATE 逐key迁移）。

**步骤二：确认该节点槲位已清空（0个槲位）**

**步骤三：将节点从集群中移除**
```bash
redis-cli --cluster del-node <节点ip:port> <节点的node-id>
```
该命令会通知集群广播该节点下线,其他节点更新拓扑信息,彻底从 Gossip 通信圈中移除。

> 注意：如果待下线的节点上还挂有从节点，需要先处理从节点（让它去复制别的主节点,或者一并下线),否则可能成为孤立节点。

### 3.4 扩容/缩容期间的注意事项

| 注意点 | 说明 |
|--------|------|
| **迁移期间性能影响** | `MIGRATE` 是逐key同步迁移,大量大key迁移时会有一定延迟,建议在低峰期操作 |
| **槲位均衡** | 扩缩容后建议检查各节点槲位数是否均匀,`redis-cli --cluster rebalance` 可自动重新均衡 |
| **客户端缓存滞后** | 迁移刚完成的瞬间，部分客户端本地缓存的槲位映射可能还没更新,会先收到一次 MOVED 重定向再纠正，这是正常现象 |
| **大key迁移阻塞** | 单个 key 过大（如几十MB的大集合）会导致 MIGRATE 单次迁移耗时变长,影响该槲位的可用性窗口,设计时应尽量避免超大 key |

### 3.5 自动化工具

实际生产环境很少手敲上述命令，通常用：
- `redis-cli --cluster` 自带的交互式/脚本化操作（如上述 `add-node` / `reshard` / `rebalance` / `del-node`）
- 云厂商托管的 Redis Cluster（阿里云/腾讯云等）通常提供**可视化扩缩容**，底层逻辑与上述一致，但隐藏了具体命令细节

---

## 总结一句话

> 扩容缩容的本质 = **槲位的迁移**，而不是数据结构的重建；正是因为有了"槲位"这个中间层，Redis Cluster 才能做到**在线、平滑、按需**的水平扩展。
