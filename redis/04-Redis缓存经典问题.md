# Redis 缓存经典问题详解

## 大纲

1. 缓存穿透 —— 查不存在的数据
2. 缓存击穿 —— 热点key过期
3. 缓存雪崩 —— 大量key同时过期
4. 缓存与数据库双写一致性

---

## 1. 缓存穿透 —— 查不存在的数据

### 1.1 问题描述

请求查询一个**数据库中也不存在**的数据。由于缓存没有，请求会穿透缓存直接打到数据库；又因为数据库里也没有，所以**永远不会写入缓存**，导致每次都打到数据库。

```
请求 → 查缓存(无) → 查数据库(无) → 返回null → 不会写缓存
下次同样的请求 → 还是要走一遍数据库
```

**危害**：如果有恶意攻击者用大量不存在的 key 发起请求（比如不存在的用户ID），数据库会被打垮。

### 1.2 解决方案

| 方案 | 原理 | 注意点 |
|------|------|--------|
| **缓存空值** | 查数据库返回null时，也把这个空结果缓存起来，设置一个较短的过期时间（如60秒） | 简单有效，但如果攻击者每次用不同的不存在key，这个方案防不住 |
| **布隆过滤器（Bloom Filter）** | 提前把所有"可能存在"的key放入布隆过滤器，请求先经过布隆过滤器判断，**一定不存在**的请求直接拒绝，根本不进缓存和数据库 | 布隆过滤器有一定误判率（可能误判"存在"但实际不存在），但不会漏判（"一定不存在"的判断是100%准确的） |
| **参数校验** | 在接口层做基础合法性校验（比如ID格式、范围），过滤明显非法的请求 | 只能拦截一部分，治标不治本 |

**布隆过滤器原理简述**：用多个哈希函数把元素映射到一个位数组的多个位置上，查询时如果**任意一个位置是0**，说明该元素**一定不存在**；如果所有位置都是1，说明该元素**可能存在**（也可能是哈希冲突导致的误判）。

## 2. 缓存击穿 —— 热点key过期

### 2.1 问题描述

某个**访问量极高的热点key**在缓存中过期的瞬间，大量并发请求同时涌入，都没有命中缓存，全部转向数据库，**瞬间压垮数据库**。

```
T0:  热点key正常,缓存命中,数据库压力正常
T1:  热点key过期了
T1+: 1000个并发请求同时到达,全部缓存未命中
     → 1000个请求同时打到数据库查询同一份数据
```

**和缓存穿透的区别**：穿透是查**根本不存在**的数据（每次都不会进缓存）；击穿是查**曾经存在、刚好过期**的热点数据（本来是会进缓存的，只是失效的瞬间出问题）。

### 2.2 解决方案

| 方案 | 原理 |
|------|------|
| **互斥锁（分布式锁）** | 缓存失效时，只允许**第一个**请求去查数据库并重建缓存，其他请求等待或重试，拿到锁的请求把数据写回缓存后释放锁，后续请求直接从缓存读 |
| **逻辑过期（不设置物理过期时间）** | 缓存value中额外存一个"逻辑过期时间"字段，缓存本身永不过期。查询时发现逻辑时间已过期，**异步**用一个线程去更新缓存，当前请求先返回旧数据（短暂的数据不一致，但不会打爆数据库） |
| **热点key永不过期 + 后台主动刷新** | 对已知的热点key（如秒杀商品）直接设置永久不过期，由后台定时任务主动更新，从根源避免"过期瞬间"这个场景 |

**互斥锁实现示意**：

```
查缓存(未命中)
  → 尝试获取分布式锁(SETNX)
    → 获取成功: 查数据库 → 写入缓存 → 释放锁
    → 获取失败: 短暂sleep后重试,或者直接返回旧值/默认值
```

## 3. 缓存雪崩 —— 大量key同时过期

### 3.1 问题描述

**大批量**的key在**同一时间点**集中过期（比如系统启动时批量缓存了大量数据，设置了相同的过期时间），导致这批key同时失效，大量请求同时穿透到数据库，造成数据库瞬时压力骤增，甚至宕机。

> 还有一种情况：**Redis 实例本身宕机/不可用**（单点故障、网络问题等），所有请求都打不到缓存，直接全部压向数据库，这也被归类为"雪崩"的一种。

**和击穿的区别**：击穿是**单个**热点key过期；雪崩是**大批量**key同时过期（或Redis整体不可用）。

### 3.2 解决方案

| 方案 | 原理 |
|------|------|
| **过期时间加随机值** | 基础过期时间 + 一个随机数（如 `expire = baseExpire + random(0,300)秒`），避免大批量key在同一时刻集中失效 |
| **多级缓存** | 本地缓存（如Caffeine/Guava Cache） + Redis分布式缓存，Redis故障时本地缓存还能兜底一部分请求 |
| **熔断/限流降级** | 数据库压力过大时，通过限流（如Sentinel/Hystrix）保护数据库，超出阈值的请求直接降级返回（比如返回默认值、排队、提示稍后重试） |
| **保证Redis高可用** | 用主从+哨兵、或Cluster分片集群，避免Redis单点故障导致全部缓存不可用 |
| **缓存预热** | 系统启动时，主动把热点数据提前加载进缓存，并打散过期时间，避免冷启动瞬间大量请求穿透 |

## 4. 缓存与数据库双写一致性

这是缓存领域**最经典也最容易踩坑**的问题：当数据**既要写数据库、又要写/删缓存**时，如何保证两者数据一致？

### 4.1 常见写策略

| 策略 | 做法 | 问题 |
|------|------|------|
| **先写缓存,再写数据库** | 更新缓存 → 更新数据库 | 如果数据库写失败，缓存里是脏数据（新值），比"先写库"的方案更危险，**不推荐** |
| **先写数据库,再写缓存** | 更新数据库 → 更新缓存 | 并发场景下仍可能出现顺序错乱（见下方案例），且"写缓存"成本高（可能涉及复杂计算） |
| **先删缓存,再写数据库** | 删除缓存 → 更新数据库 | 并发读请求在"删除缓存"和"写数据库"之间的窗口期，会把**旧数据**重新加载回缓存（见下方详解） |
| **先写数据库,再删缓存（Cache Aside,推荐）** | 更新数据库 → 删除缓存（让下次读时重新从数据库加载最新值） | 业界主流方案，但仍有极小概率的并发问题（见下） |

### 4.2 为什么推荐"更新数据库 + 删除缓存"（而不是更新缓存）

- **删除**比**更新**更简单、更安全：不用关心要写入什么值，下次读取时自然会从数据库拿最新值重建缓存
- 如果是"更新缓存"，遇到复杂计算的value（比如要联表查询、聚合统计），每次更新都要重新算一遍，开销大；而且并发写时多个值互相覆盖的顺序更难控制

### 4.3 "先删缓存再写库"的并发问题

```
T0: 缓存中 key=value_old
T1: 线程A删除缓存
T2: 线程B此时来读 → 缓存未命中 → 查数据库(此时数据库还是旧值,因为A还没写完)
T3: 线程B把 value_old 写回缓存
T4: 线程A更新数据库为 value_new
    → 最终缓存里是 value_old,数据库里是 value_new,数据不一致!
    → 而且这个脏数据会一直留在缓存里,直到下次主动更新或自然过期
```

### 4.4 "先写库再删缓存"也有小概率问题（但窗口期短得多）

```
T0: 线程A读缓存未命中,准备查数据库(还没查完)
T1: 线程B更新数据库为 value_new,并删除缓存
T2: 线程A才查到旧值 value_old(因为它在T0就开始查了,查的是更新前的数据)
T3: 线程A把 value_old 写回缓存
    → 缓存变脏
```

**这种情况概率极低**：因为写操作通常比读操作慢（要写数据库），读操作在写操作"删除缓存"之前就已经把旧值缓存的窗口非常窄。业界普遍认为这种极端情况**可以接受**，所以"先写库,再删缓存"（Cache Aside模式）仍是**业界主流推荐方案**。

### 4.5 进一步加固方案

| 方案 | 解决思路 |
|------|---------|
| **延迟双删** | 删除缓存 → 更新数据库 → **休眠一段时间**（比如500ms,确保其他并发读请求已经把脏数据写完） → **再删一次缓存**,清掉可能被脏写入的旧值 |
| **重试机制 + 消息队列** | 删除缓存操作失败时，扔进MQ异步重试，保证"删除"这个动作最终一定会成功执行（借助MQ的重试/死信队列能力） |
| **订阅数据库变更日志（如阿里的Canal）** | 监听MySQL的binlog，数据库一旦发生变更，通过Canal自动触发缓存删除/更新，把"双写"问题转变为"监听binlog做单一动作"，从根源上避免业务代码里写两套逻辑导致的不一致风险 |
| **设置较短的缓存过期时间兜底** | 即使出现极端情况下的脏数据，也只会存在到下一次过期，把"最终一致性"的恢复时间收窄到可接受范围 |

> **澄清一个常见误解**：缓存与数据库的一致性，在绝大多数业务场景下追求的是**最终一致性**，而不是强一致性。真正要强一致（比如金融转账核心字段），应该走分布式事务、或者直接不用缓存读这类数据。

## 总结对比表

| 问题 | 触发条件 | 核心解法 |
|------|---------|---------|
| 缓存穿透 | 查询不存在的数据 | 缓存空值 + 布隆过滤器 |
| 缓存击穿 | 单个热点key过期 | 互斥锁 / 逻辑过期 / 永不过期+后台刷新 |
| 缓存雪崩 | 大批量key同时过期 / Redis宕机 | 过期时间加随机值 + 多级缓存 + 高可用部署 |
| 双写一致性 | 数据库与缓存数据不同步 | 先写库再删缓存(Cache Aside) + 延迟双删/Canal兜底 |
