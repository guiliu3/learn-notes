# 04-Kafka 项目实战问题

> 学习目标：把 Kafka 原理落到你的“政务数据同步平台”项目中，形成能直接用于面试的表达：为什么选 Kafka、如何保证可靠性、如何处理幂等、失败补偿、消费积压、事务边界和后续优化。

## 一、项目背景复述

你的项目可以这样概括：

> 这个数据同步平台主要是为了解决原有 Kettle/Spoon 定时同步方案实时性差、维护困难、失败补偿不灵活的问题。平台基于 Kafka 和 Spring Cloud Stream 构建异步数据同步链路，实现门户系统、云平台、电子监察等多个系统之间的业务数据流转。

核心技术：

- Spring Boot。
- Kafka。
- Spring Cloud Stream。
- XXL-Job。
- Baomidou Dynamic Datasource。
- 责任链模式。
- ThreadLocal 上下文。
- Redis 成功标记。
- REST API 手动补偿。

你的项目角色应该突出：

- 参与数据同步链路设计。
- 负责 Kafka 消费处理和多数据源切换。
- 使用责任链模式编排多表同步。
- 设计补偿和幂等策略。

## 二、项目架构表达

简化架构：

```text
门户系统 / 源系统
   |
   | 产生业务事件，发送 bizId
   v
Kafka Topic
   |
   v
数据同步 Consumer
   |
   | 根据 bizId 查询源库完整数据
   v
ThreadLocal 同步上下文
   |
   v
责任链 Handler
   |-- 主表同步 Handler
   |-- 子表同步 Handler
   |-- 附件同步 Handler
   |-- 日志同步 Handler
   |
   v
目标系统数据库
   |
   v

```

补偿链路：

```text
XXL-Job 定时扫描 / REST API 手动触发
   |
   v
按时间范围和同步状态筛选未成功数据
   |
   v
重新发送 Kafka
   |
   v
Consumer 重新执行同步
```

## 三、为什么不用同步接口调用

问题点：

- 门户系统会直接依赖多个下游系统。
- 下游接口慢会拖慢主业务接口。
- 下游系统不可用会影响门户申请流程。
- 新增下游系统时，门户系统需要改造。
- 多个系统同步成功/失败难以统一管理。

面试回答：

> 如果采用同步接口调用，门户系统需要直接依赖审批端、电子监察、云平台等多个下游系统。一旦下游接口响应慢或不可用，就会拖慢甚至影响门户主业务。我们希望门户系统只负责业务受理，数据流转交给异步同步平台处理，所以选择 Kafka 做解耦。门户只发送业务事件，下游消费者按自己的节奏处理，系统之间的耦合度更低。

## 四、为什么不用 Kettle/Spoon

原方案问题：

- 定时同步，实时性差。
- 串行任务多，链路长。
- 失败补偿依赖人工处理。
- 复杂业务逻辑维护困难。
- 监控和问题定位不直观。

面试回答：

> Kettle 更适合批量 ETL，但我们这个场景需要门户申请后尽快同步到审批端和监管系统。定时任务会带来同步延迟，而且复杂业务逻辑写在 Kettle 任务里维护成本比较高。Kafka 方案可以把数据同步事件化，消费者侧用 Java 代码实现责任链处理，扩展和排查都更方便。

## 五、为什么选择 Kafka

Kafka 解决的问题：

- 异步解耦。
- 削峰填谷。
- 消息持久化。
- 多消费者订阅。
- 水平扩展。
- 适合数据同步场景。

面试回答：

> Kafka 在这个项目中主要承担异步解耦和可靠传输的角色。门户系统产生业务事件后写入 Kafka，不需要等待下游系统处理完成。同步服务作为消费者从 Kafka 拉取消息，再根据业务唯一值查询源数据并写入目标系统。这样主业务和同步流程分离，下游系统异常也不会直接影响门户申请。

注意表达边界：

> Kafka 不等于绝对不丢、不重复。项目可靠性还要靠生产端确认、消费端 Offset 控制、业务幂等和补偿机制共同保证。

## 六、为什么使用 Spring Cloud Stream

优点：

- 与 Spring Boot 集成简单。
- 屏蔽部分 Kafka API 细节。
- 统一生产者和消费者开发模型。
- 团队维护成本低。
- 以后理论上可切换消息中间件。

面试回答：

> 当时选择 Spring Cloud Stream，主要是为了降低团队接入 Kafka 的复杂度。它把底层 Kafka API 做了一层抽象，业务代码更关注消息内容和业务处理本身。对于团队协作和后续维护来说，比直接使用 KafkaTemplate 更统一。

补充：

> 如果对 Kafka 参数控制要求很细，比如事务、精细化 Offset、复杂拦截器，也可以直接使用 Kafka 原生客户端或 Spring Kafka。

## 七、消息为什么只放业务唯一值

你的项目原表达是只发送业务唯一值。

优点：

- 消息体小。
- Producer 压力低。
- 消息格式稳定。
- Consumer 可以查询源库最新数据。
- 后续字段变化时，不需要频繁改消息结构。

缺点：

- Consumer 依赖源库。
- 源库不可用会导致消费失败。
- 消费时拿到的是当前数据，不一定是事件发生瞬间的数据快照。
- 对事件溯源不友好。

面试回答：

> 我们当时 Kafka 消息里主要放业务唯一值，消费者拿到业务 ID 后再查源库完整数据。这样可以降低消息体大小和 Producer 组装成本，也避免业务字段频繁变化导致消息结构不稳定。这个方案适合当时的数据同步场景，因为我们更关注同步当前业务数据状态。如果业务要求保留事件发生瞬间的完整快照，就应该把关键字段和事件版本一起放进消息。

## 八、如何保证消息可靠性

完整方案应该从三端回答。

### 1. 生产端

措施：

- `acks=all`。
- 开启重试。
- 开启幂等生产者。
- 发送失败记录失败状态。
- 本地消息表或同步事件表。

回答：

> 生产端可以通过 `acks=all`、重试和幂等生产者降低消息发送丢失风险。业务侧最好记录发送状态，发送失败的数据由定时任务扫描后重新发送。

### 2. Broker 端

措施：

- 多 Broker 部署。
- Partition 多副本。
- ISR 机制。
- 合理配置副本数和最小同步副本数。

回答：

> Broker 端依靠副本机制保证高可用。每个 Partition 有 Leader 和 Follower，Leader 故障后从同步副本中选举新的 Leader。

### 3. 消费端

措施：

- 关闭自动提交。
- 业务处理成功后提交 Offset。
- 消费失败记录失败原因。
- 消费端业务幂等。
- 重试和死信。

回答：

> 消费端更关键。我们不能在业务成功前提交 Offset，否则业务失败就会丢消息。通常是先处理业务，再提交 Offset，重复消费通过业务唯一键幂等解决。

项目实话表达：

> 当时项目没有做到完整自动死信和重试，主要采用人工可控补偿。后续优化会补失败记录表、重试次数、错误原因、死信 Topic 和告警。

## 九、如何处理重复消费

重复来源：

- Producer 重试。
- Consumer 处理成功但 Offset 提交失败。
- Rebalance。
- 补偿任务重新发送。
- 人工重复触发。

项目方案：

- 使用业务唯一主键。
- 目标表唯一索引。
- Redis 成功标记减少重复补推。
- 下游按业务主键插入或更新。

面试回答：

> 我们不假设 Kafka 消息只会消费一次，而是在业务层做幂等。补偿任务可能重复推送消息，Consumer 也可能重复消费，所以目标系统以业务唯一主键作为幂等键。如果数据已存在，就执行更新或跳过，避免生成重复数据。

更成熟的优化：

- 增加消费记录表。
- 记录 `topic + partition + offset + biz_id`。
- 对 `biz_id + event_type` 建唯一索引。
- 对状态流转做版本控制。

## 十、如何处理消费失败

当前项目：

- 没有自动失败重试。
- 没有死信队列。
- 主要依靠人工可控补偿。
- 根据同步状态和时间范围重新触发。

这样回答比较稳：

> 当时项目考虑到政务数据同步需要人工确认补推范围，没有做无限自动重试，而是采用人工可控补偿。每条数据有同步状态和时间戳，发现异常后可以通过 REST API 按时间范围重新触发补推。这个方案可控，但自动化程度不足。后续我会增加失败记录表、重试次数、错误原因、死信 Topic 和补偿后台。

推荐优化流程：

```text
消费失败
  |
  v
记录失败表，retry_count + 1
  |
  v
判断是否超过最大重试次数
  |
  |-- 未超过：延迟重试
  |
  |-- 超过：进入死信 Topic / 人工补偿
```

## 十一、如何处理消费积压

排查路径：

1. 看 Consumer Lag。
2. 看 Producer 生产速度是否突增。
3. 看 Consumer 实例数是否不足。
4. 看 Partition 数量是否限制并行度。
5. 看单条消息处理耗时。
6. 看目标库是否慢 SQL 或锁等待。
7. 看失败消息是否反复重试阻塞。

解决方式：

- 增加 Consumer 实例。
- 增加 Partition 数量。
- 优化 Handler 逻辑。
- 批量写入数据库。
- 优化目标表索引。
- 慢消息转失败表，不阻塞主链路。
- 对下游限流，避免压垮数据库。

面试回答：

> 消费积压不能只说加机器。要先看 Lag，再判断瓶颈在 Kafka 消费能力、业务处理逻辑还是下游数据库。如果 Partition 数量只有 3 个，加到 10 个 Consumer 也没用，因为同一个消费者组最大并行度受 Partition 数量限制。

## 十二、事务边界怎么处理

你的项目会被追问：

> Handler 处理到一半失败，前面已入库的数据怎么办？

回答要分情况。

### 1. 同一个目标库

可以在责任链外层加事务：

```text
Consumer 收到消息
  |
  v
@Transactional
  |
  |-- Handler 1 写主表
  |-- Handler 2 写子表
  |-- Handler 3 写附件表
  |
  v
全部成功提交，失败回滚
```

回答：

> 如果这些 Handler 写的是同一个目标库，可以在责任链外层 Service 方法加事务，任一 Handler 失败就抛异常，前面写入一起回滚。

### 2. 多数据源 / 多系统

普通本地事务不够。

可选方案：

- 幂等 + 补偿。
- 最终一致性。
- Saga。
- TCC。
- 分布式事务框架。

你的项目建议表达：

> 我们这个项目没有做强一致分布式事务，主要通过业务主键幂等和补偿机制保证最终一致。因为政务数据同步更关注最终数据一致和可追溯，出现异常时可以按业务范围补推。

## 十三、为什么使用责任链

业务特点：

- 一个办件涉及多张表。
- 每张表处理逻辑不同。
- 处理顺序有前后依赖。
- 后续可能新增业务节点。

面试回答：

> 一个业务同步通常涉及主表、子表、附件、日志等多个处理节点。每个节点职责不同，但整体流程一致。使用责任链后，每个 Handler 只处理自己的业务表，公共逻辑放在抽象父类，新增节点只需要新增 Handler 并加入链路，不需要在主流程里写大量 if-else。

## 十四、为什么使用 ThreadLocal

用途：

- 在一次消费任务中共享源业务数据。
- 避免每个 Handler 重复查库。
- 避免方法参数层层传递。

风险：

- 线程池复用导致脏数据。
- 忘记 remove 造成内存泄漏。

面试回答：

> 我们使用 ThreadLocal 保存当前同步任务的上下文，入口处一次性查询源业务数据，各个 Handler 从上下文中获取，避免重复查库和层层传参。因为消费者线程会复用，所以必须在 finally 中执行 `ThreadLocal.remove()`，避免脏数据和内存泄漏。

## 十六、项目面试高频问答

### 1. 你们怎么保证 Kafka 消息不丢

答：

> 这个问题要分生产端、Broker 和消费端。生产端可以通过 `acks=all`、重试、幂等生产者和发送状态记录降低丢失风险；Broker 端通过副本和 ISR 保证可用性；消费端要在业务处理成功后再提交 Offset，失败时记录失败原因并进入补偿流程。我们项目当时主要做了状态标记和人工补偿，后续可以补自动重试和死信。

### 2. 你们怎么保证不重复同步

答：

> Kafka 本身不能保证业务绝对不重复，所以我们基于业务唯一主键做幂等。补推或重复消费时，下游系统用相同业务主键做插入或更新，不会生成多条重复数据。同时补偿任务会参考 Redis 成功标记，减少重复推送。

### 3. 如果 Consumer 消费到一半宕机怎么办

答：

> 如果业务没有处理成功，就不应该提交 Offset，Consumer 重启后会从上次提交的 Offset 继续消费，可能出现重复消费。重复消费通过业务幂等处理。如果部分表已经写入，需要看是否在同一个本地事务内；同库可以回滚，多数据源则依赖幂等和补偿保证最终一致。

### 4. 如果下游数据库慢导致消费积压怎么办

答：

> 先看 Consumer Lag 和单条处理耗时，确认瓶颈是否在数据库。如果是数据库慢，需要看慢 SQL、索引、锁等待和连接池。短期可以增加消费者实例，但前提是 Partition 数量足够；长期要优化 Handler 逻辑、批量写入、索引和失败消息隔离。

### 5. 为什么不用 RabbitMQ

答：

> RabbitMQ 更适合传统业务队列、复杂路由和延迟队列。我们这个项目是多系统数据同步，更关注高吞吐、消息持久化、多消费者订阅和数据流转，所以 Kafka 更匹配。当然如果业务是低吞吐的任务分发和复杂路由，RabbitMQ 也可以。

### 6. Kafka 能保证顺序吗

答：

> Kafka 只能保证单个 Partition 内有序，不能保证 Topic 全局有序。如果同一个办件的状态变更要求顺序处理，需要用办件唯一 ID 作为 Key，让同一办件的消息进入同一个 Partition。

### 7. 你们的方案有什么不足

答：

> 当时方案满足了业务同步和人工补偿要求，但自动化治理还不够，比如没有完整死信队列、失败重试表、消费积压告警和补偿后台。如果后续优化，我会把失败消息、重试次数、错误原因、消费延迟和补偿操作都平台化。

## 十七、项目表达模板

### 1 分钟版本

> 这个项目是政务数据同步平台，主要解决原来 Kettle 定时同步实时性差、维护困难的问题。我们基于 Kafka 做异步解耦，门户系统产生业务事件后发送业务唯一值到 Kafka，消费者拿到消息后查询源库完整数据，通过责任链模式同步主表、子表、附件等多张业务表到目标系统。为了处理重复和失败，我们用业务唯一主键做幂等，并提供按时间范围和状态的补偿接口。这个方案把主业务和数据同步解耦，提高了实时性和可维护性。

### 3 分钟版本

> 这个平台最初是为了替代 Kettle/Spoon。原来的方案主要靠定时任务同步，实时性不好，失败后补偿也不方便。我们改成 Kafka 事件驱动模式，门户系统在业务受理后只发送业务唯一 ID 到 Kafka，不直接调用下游系统。同步服务作为 Consumer 拉取消息，根据业务 ID 查询源库完整数据，然后放入 ThreadLocal 上下文，通过责任链 Handler 依次同步不同业务表。
>
> 这样做有几个好处。第一，门户主业务不被下游系统拖慢；第二，新增下游同步逻辑时扩展 Handler 即可；第三，补偿时可以按业务状态和时间范围重新触发。可靠性方面，我们不宣称 Exactly Once，而是通过业务唯一键幂等和补偿机制保证最终一致。如果后续优化，我会补充消费失败表、死信 Topic、自动重试、Consumer Lag 监控和补偿后台。

## 十九、今天记住的三句话

- 项目里 Kafka 的价值是异步解耦、可靠传输、削峰和多下游扩展，不是为了炫技。
- Kafka 不保证业务绝对不重复，数据同步平台必须依靠业务唯一键、幂等和补偿保证最终一致。
- 面试时要敢于承认当前方案不足，并给出后续优化方案：失败记录、重试、死信、监控、补偿后台。
