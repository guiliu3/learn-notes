**1.你现在有一个“政务数据同步平台”，包含：业务源数据提交、Kafka 消息生产、Kafka 消费同步、失败补偿、人工重推、同步状态查询、告警通知。 如果让你把它从一个单体应用演进成微服务，你会怎么拆？**
>答：我会按业务能力拆，不按技术层拆。数据同步平台可以拆成业务源服务、同步生产服务、同步消费服务、补偿任务服务和同步管理服务。业务源服务负责业务提交和同步状态维护；同步生产服务只负责生成同步事件；消费服务负责根据业务主键查询源数据并写入目
> 标库；补偿服务负责扫描失败、超时、未同步数据并重推；管理服务负责失败记录查询、人工补偿和状态查看。
> 但我不会拆得过细，比如告警、日志、状态查询前期可以归到管理或补偿服务里，避免调用链太长。拆分后会带来远程调用、事务一致性、链路追踪、部署复杂度和故障隔离问题。事务上我不会追求跨服务强一致，而是每个服务内部保证本地事务，跨服务通过
> Kafka、业务状态、幂等主键、唯一索引、失败表和补偿任务保证最终一致。


**2.你们项目用了 Nacos 吗？如果用了，它在数据同步平台里具体解决了什么问题？如果 Nacos 挂了，业务还能不能正常运行？**
>答： 我们项目里 Nacos 主要做注册中心和配置中心。注册中心用于服务注册发现，比如同步管理服务调用补偿服务，不需要写死 IP，而是通过服务名从 Nacos 获取实例列表，再通过负载均衡选择实例。配置中心用于统一管理 Kafka topic、consumer group、消费开
> 关、补偿批次、最大重试次数、告警开关、限流阈值等配置，部分开关和阈值可以动态调整，不需要每次重新发版。
> 如果 Nacos 短时间挂了，已经缓存的服务实例一般还能继续调用，但新实例注册、下线感知、配置变更会受影响。所以生产环境不能单点部署 Nacos，要做集群；调用侧也要有超时、熔断和降级，不能完全依赖注册中心。

**你的数据同步平台有一个“人工补偿重推”接口，运维人员可以选择失败数据重新推送。 如果这个接口暴露在管理后台，你会在 Gateway 层做哪些保护？为什么？**
>答： 人工补偿重推是高风险接口，我会在 Gateway 层先做统一鉴权和角色校验，只有具备补偿权限的运维或管理员才能操作。第二，会做接口限流和参数限制，比如限制单次补偿数量、请求频率、业务类型和时间范围，避免一次性重推大量失败数据，把 Kafka、数据库
> 或目标系统压垮。第三，会记录审计日志，包括操作人、业务主键、补偿批次、请求参数、traceId、执行结果。第四，Gateway 会透传 traceId，方便后续从管理端追到补偿服务、Kafka 消费者和目标库写入。对于重复点击或重复请求，后端还需要用业务主键和补
> 偿批次做幂等控制。

**数据同步平台里，为什么主同步链路你选择 Kafka，而不是用 OpenFeign 直接从业务源服务调用目标系统接口完成同步？ 你怎么向面试官解释这个技术取舍？**
>答：> 数据同步主链路我会选择 Kafka，而不是 OpenFeign。因为 Feign 是同步调用，如果业务源服务提交数据时直接调用目标系统，一旦目标系统慢、网络抖动、接口超时，就会阻塞业务源服务，甚至拖垮上游线程池。
> Kafka 的价值是把业务提交和数据同步解耦。业务源只需要提交数据并发送业务主键消息，后续由消费者异步同步到目标库。这样可以削峰，也可以通过消费位点、失败表、重试、补偿任务和 DLQ 来保证最终一致。
> Feign 更适合管理后台查询同步状态、触发补偿任务这类需要实时返回的内部调用，不适合承担大批量、可重试、需要补偿的数据同步主链路。

**假设你有一个 Feign 接口 createSyncTask()，用于创建同步任务。调用方请求超时了，但其实下游可能已经创建成功。 这时候调用方能不能直接重试？为什么？你会怎么设计？**
>答：不能直接重试。Feign 超时后，调用方并不知道下游到底有没有执行成功，可能只是响应返回慢。如果下游已经创建了同步任务，再重试就会重复创建。
> 我的设计是让调用方传一个业务唯一请求号，比如业务主键加同步类型，目标服务基于这个唯一键建唯一索引。创建任务时先判断是否存在，如果已存在，就返回已有任务状态；如果不存在，再创建。状态上可以设计 pending、processing、success、fail，重复请
> 求只能查询或推进状态，不能重复插入。
> 如果要重试，也只能对幂等接口做有限重试，并且要设置超时时间、重试次数和告警。

**中考成绩查询系统在成绩开放当天，访问量突然暴涨。你会用 Sentinel 保护哪些资源？分别用限流、熔断、降级解决什么问题？**
>答： > 我会保护几个资源：第一是成绩查询接口，基于压测结果设置 QPS 限流，防止开放查询瞬间流量直接打满应用；第二是准考证号或学校 ID 这类热点参数，可以做热点参数限流，防止某些参数被刷；第三是数据库查询方法，可以设置线程数限流，避免慢 SQL 时大
> 量请求占满线程池和数据库连接池；第四是下游 Feign 调用，如果慢调用比例或异常比例升高，就触发熔断。
> 限流解决入口流量过大，熔断解决下游慢或异常导致故障扩散，降级是在限流或熔断后返回“查询中”“系统繁忙请稍后重试”或者缓存结果，优先保证查询主链路不被拖垮。

**线上现象：中考查询系统突然大量超时，Gateway 日志显示请求进来了，但很多请求 5 秒后失败。Sentinel 也开始大量限流，数据库连接池接近打满，Redis 命中率从 90% 掉到 40%。 你会怎么排查？请按优先级说。**
>答： > 我会先止血，防止数据库被继续打满，比如临时收紧 Gateway 或 Sentinel 限流，对非法准考证号直接拦截，必要时返回查询繁忙。然后看请求分布，按 IP、准考证号、学校维度统计，判断是否有爬虫、刷接口或热点参数。
> Redis 命中率从 90% 掉到 40%，说明大量请求没有命中缓存，可能是缓存穿透、缓存雪崩或 key 规则异常。我会重点看是否存在大量伪造准考证号，如果是，就做准考证号格式和范围校验，并对不存在的数据缓存空值或使用布隆过滤器。
> 同时排查 Redis key 是否集中失效、TTL 是否过短、是否没有预热。数据库侧看慢 SQL、索引命中、连接池等待和锁等待。应用侧看 Tomcat 线程、Sentinel 触发资源、接口 RT 和 GC。恢复后要补缓存预热、热点参数限流、非法请求拦截和监控告警。

**你对Spring Cloud微服务治理如何理解的，以及它在你项目里如何落地？**
>答： > 我理解 Spring Cloud 不是单个组件，而是一套微服务治理体系。服务拆分以后，原来单体里的本地调用变成了远程调用，原来本地配置变成了多服务多环境配置，原来一个应用里的异常也可能变成跨服务故障扩散。所以微服务落地不只是拆服务，还必须配套注册
> 发现、配置中心、网关、远程调用、限流熔断、链路追踪和监控告警。
> 在服务拆分上，我不会按 controller、service、mapper 这种技术层拆，而是按业务能力拆。比如数据同步平台可以拆成业务源服务、同步生产服务、同步消费服务、补偿任务服务和同步管理服务。业务源服务负责业务提交和同步状态维护，同步生产服务负责发
> Kafka 消息，消费服务负责同步目标库，补偿服务负责失败重推，管理服务负责失败记录查询和人工补偿。拆完以后会带来跨服务调用、事务一致性和排查复杂度问题，所以跨服务不追求强事务，而是通过 Kafka、状态表、幂等主键、唯一索引、失败记录和补偿任
> 务保证最终一致。
> Nacos 在这里承担注册中心和配置中心。注册中心让服务通过服务名发现彼此，不需要写死 IP；配置中心统一管理 Kafka topic、consumer group、消费开关、补偿批次、最大重试次数、告警开关、限流阈值等配置。Nacos 短时间不可用时，客户端缓存的服务列表
> 还能支撑已有调用，但新实例注册、下线感知和配置刷新会受影响，所以生产要集群部署。
> Gateway 是统一入口，主要做路由、鉴权、限流、日志和审计。比如数据同步平台的人工补偿、失败查询、任务开关这些管理接口要经过 Gateway，做角色权限校验、参数限制、限流和操作审计，避免无权限人员或批量重推把系统压垮。
> OpenFeign 适合同步内部调用，比如管理服务查询补偿服务状态、调用权限服务校验用户身份。但主同步链路我不会用 Feign，而会用 Kafka，因为 Feign 是同步调用，下游慢会阻塞上游线程；Kafka 更适合异步解耦、削峰、失败重试和最终一致。使用 Feign 时
> 必须设置连接超时、读取超时，重试只适合幂等接口，写接口要有业务唯一键和唯一索引。
> Sentinel 负责限流、熔断和降级。限流解决入口流量过大，熔断解决下游慢或异常导致故障扩散，降级是在异常时返回兜底结果。比如中考查询系统中，可以对成绩查询接口做 QPS 限流，对准考证号做热点参数限流，对数据库查询方法做线程数限流；如果下游服
> 务慢调用比例升高，就熔断并返回“查询中”或“请稍后重试”。
> 所以我理解的 Spring Cloud 落地，不是简单引入 Nacos、Gateway、Feign、Sentinel，而是围绕服务拆分后的稳定性问题做治理：服务怎么发现，配置怎么管理，入口怎么保护，远程调用怎么控制超时和重试，下游异常怎么熔断降级，最后通过日志、traceId 和
> 监控把问题排查闭环。
