# 03-Gateway网关与鉴权限流

## 1. 面试先给结论

Gateway 是微服务系统的统一入口，核心职责不是简单转发请求，而是做统一路由、鉴权、限流、日志、跨域、灰度和协议适配。

面试表达可以这样说：

> Gateway 位于客户端和后端服务之间，负责统一接入流量。它可以根据路径、域名、Header 等条件把请求路由到不同服务，同时在入口层做统一鉴权、限流、日志记录和灰度发布。这样可以避免每个业务服务重复处理通用能力，也能在流量进入系统前做第一层保护。

## 2. 为什么需要网关

如果没有网关，客户端需要直接访问多个后端服务：

```text
客户端 -> 用户服务
客户端 -> 查询服务
客户端 -> 管理服务
客户端 -> 同步服务
```

问题：

- 客户端需要知道多个服务地址。
- 每个服务都要重复做鉴权。
- 跨域、日志、限流逻辑分散。
- 服务地址变化会影响客户端。
- 缺少统一入口控制。

引入 Gateway 后：

```text
客户端 -> Gateway -> 后端服务
```

价值：

- 统一入口。
- 统一鉴权。
- 统一限流。
- 统一日志。
- 动态路由。
- 灰度发布。
- 屏蔽内部服务地址。

## 3. Gateway 的核心概念

### 3.1 Route 路由

路由定义了请求要转发到哪里。

一个路由通常包含：

- 路由 ID。
- 目标服务 URI。
- Predicate 断言。
- Filter 过滤器。

示例：

```yaml
spring:
  cloud:
    gateway:
      routes:
        - id: exam-query-route
          uri: lb://exam-query-service
          predicates:
            - Path=/api/query/**
          filters:
            - StripPrefix=1
```

含义：

- 请求路径匹配 `/api/query/**`。
- 转发到 `exam-query-service`。
- `lb://` 表示结合注册中心做负载均衡。

### 3.2 Predicate 断言

Predicate 用来判断请求是否匹配某个路由。

常见条件：

- Path：按路径匹配。
- Host：按域名匹配。
- Method：按请求方法匹配。
- Header：按请求头匹配。
- Query：按请求参数匹配。
- Cookie：按 Cookie 匹配。

### 3.3 Filter 过滤器

Filter 用于在请求转发前后做处理。

常见用途：

- 鉴权。
- 日志。
- 限流。
- 修改请求头。
- 修改响应头。
- 统一异常处理。
- 灰度路由。

Filter 分为：

- GlobalFilter：全局过滤器，对所有请求生效。
- GatewayFilter：局部过滤器，只对指定路由生效。

## 4. Gateway 和 Nginx 的区别

Nginx 和 Gateway 都可以做入口转发，但侧重点不同。

Nginx 更偏基础设施层：

- 静态资源。
- 反向代理。
- 负载均衡。
- TLS 终止。
- 基础限流。

Gateway 更偏业务网关：

- 服务路由。
- 统一鉴权。
- 用户上下文传递。
- 业务限流。
- 灰度发布。
- 与注册中心集成。

面试表达：

> Nginx 一般作为更靠前的七层入口，负责域名、证书、静态资源和基础转发；Gateway 更靠近业务系统，负责微服务路由、鉴权、限流、灰度和统一日志。两者不是互相替代，而是可以配合使用。

典型链路：

```text
用户 -> Nginx -> Gateway -> 微服务
```

## 5. Gateway 鉴权设计

### 5.1 为什么鉴权放网关

鉴权是通用能力，如果每个服务都自己做，会带来：

- 重复代码多。
- 权限规则不一致。
- 修改成本高。
- 容易漏鉴权。

放在网关的好处：

- 统一校验登录态。
- 统一解析 Token。
- 统一拦截非法请求。
- 统一传递用户上下文。

### 5.2 常见鉴权流程

```text
1. 客户端携带 Token 请求 Gateway。
2. Gateway 校验 Token 是否存在。
3. Gateway 解析 Token，获取用户 ID、角色、权限。
4. Gateway 判断当前路径是否允许访问。
5. 校验通过后，把用户上下文放入 Header。
6. 后端服务从 Header 获取用户信息。
```

示例 Header：

```text
X-User-Id: 10001
X-User-Name: zhangsan
X-Tenant-Id: tenant001
```

注意：

- 后端服务不能盲目信任外部传入的用户 Header。
- 用户 Header 应该由 Gateway 内部设置。
- Nginx 或 Gateway 要清理客户端伪造的敏感 Header。

## 6. Gateway 限流设计

### 6.1 为什么入口要限流

限流的目的不是让系统更快，而是保护系统在高峰或异常流量下不被打垮。

限流可以放在多个层次：

- Nginx 限流。
- Gateway 限流。
- 应用接口限流。
- Redis 分布式限流。
- Sentinel 资源限流。

### 6.2 Gateway 限流适合什么

Gateway 适合做入口级限流：

- 按 IP 限流。
- 按用户限流。
- 按接口路径限流。
- 按租户限流。
- 按服务维度限流。

比如：

```text
/api/query/** 每秒最多 2000 个请求
/api/admin/** 每秒最多 200 个请求
单个 IP 每秒最多 5 次查询
```

### 6.3 常见限流算法

固定窗口：

- 实现简单。
- 窗口边界可能有突刺。

滑动窗口：

- 比固定窗口更平滑。
- 实现复杂一些。

令牌桶：

- 按固定速率生成令牌。
- 可以允许一定突发流量。

漏桶：

- 请求按固定速率流出。
- 更强调平滑处理。

面试表达：

> 实际项目里，我会更关注限流放在哪一层、按什么维度限流、超过阈值后怎么降级。算法上常见是令牌桶和滑动窗口。入口层可以先做粗粒度保护，应用层再结合业务做精细控制。

## 7. Gateway 灰度发布

灰度发布可以让一部分流量先进入新版本。

常见维度：

- 按用户 ID。
- 按租户。
- 按 Header。
- 按 IP。
- 按比例。

示例：

```text
普通用户 -> query-service-v1
测试用户 -> query-service-v2
Header: X-Gray=true -> query-service-v2
```

价值：

- 降低发布风险。
- 验证新版本稳定性。
- 出问题可以快速切回旧版本。

## 8. Gateway 日志与链路追踪

网关是请求入口，适合生成或透传 traceId。

典型流程：

```text
1. 请求进入 Gateway。
2. 如果 Header 没有 traceId，则生成一个。
3. 写入请求 Header。
4. 后端服务日志统一打印 traceId。
5. 排查问题时通过 traceId 串起全链路日志。
```

需要记录：

- traceId。
- 请求路径。
- 请求方法。
- 用户 ID。
- 来源 IP。
- 目标服务。
- 响应状态码。
- 耗时。
- 异常信息。

## 9. 项目一：中考查询系统怎么用 Gateway

中考查询系统高峰期流量集中，Gateway 可以做第一层入口保护。

可以设计：

- `/api/query/**` 路由到查询服务。
- `/api/admin/**` 路由到后台管理服务。
- 查询接口按 IP、准考证号、用户维度限流。
- 查询开放时间由配置中心控制。
- 查询高峰期对非核心接口降级。
- 网关统一记录 traceId、用户信息、耗时。

面试表达：

> 中考查询系统里，我会把 Gateway 作为统一入口，查询接口和后台接口分开路由。查询高峰期，在 Gateway 层先按 IP 和接口做粗粒度限流，防止异常流量直接打到应用；应用层再结合 Redis 做准考证号或用户维度的业务限流。同时通过 traceId 串起网关、查询服务、Redis 和数据库日志。

## 10. 项目二：数据同步平台怎么用 Gateway

数据同步平台一般不需要把 Kafka 消费链路暴露给外部，但管理能力可以通过 Gateway 暴露。

适合经过 Gateway 的接口：

- 同步失败记录查询。
- 人工补偿重推。
- 同步状态查看。
- 同步任务开关。
- 告警规则管理。

需要重点保护：

- 人工重推接口必须鉴权。
- 批量补偿接口要限流。
- 危险操作要审计。
- 后台接口要区分角色权限。

面试表达：

> 数据同步平台中，核心消费链路不走 Gateway，但管理后台接口会经过 Gateway。比如失败记录查询、人工重推、同步开关调整，这些操作需要统一鉴权、限流和审计。特别是补偿重推接口，如果不限制批量和频率，可能会对 Kafka、数据库和下游系统造成压力。

## 11. 高频问题

### 11.1 Gateway 的作用是什么

答法：

> Gateway 是微服务统一入口，负责路由转发、鉴权、限流、日志、跨域、灰度等通用能力。它可以屏蔽内部服务地址，让客户端只访问统一入口。

### 11.2 Gateway 和 Nginx 有什么区别

答法：

> Nginx 更偏基础设施，处理域名、证书、静态资源、基础反向代理；Gateway 更偏业务网关，处理服务路由、鉴权、限流、用户上下文、灰度发布。生产中经常是 Nginx 在前，Gateway 在后。

### 11.3 为什么鉴权放网关

答法：

> 鉴权是通用能力，放在网关可以统一校验 Token、统一拦截非法请求、统一传递用户上下文，避免每个服务重复实现。但后端服务也要保护内部接口，不能完全依赖网关。

### 11.4 Gateway 限流和应用限流有什么区别

答法：

> Gateway 限流更适合入口层粗粒度保护，比如按 IP、接口、用户限流；应用限流更适合结合业务规则做精细控制，比如按准考证号、订单号、租户、业务状态限流。两者可以组合使用。

### 11.5 Gateway 出问题会不会影响全站

答法：

> 会，因为 Gateway 是统一入口，所以它本身必须高可用部署，通常多实例部署在 Nginx 后面。同时要控制网关逻辑复杂度，避免把大量业务逻辑放到网关里。
