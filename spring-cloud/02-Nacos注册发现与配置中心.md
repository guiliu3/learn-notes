# 02-Nacos注册发现与配置中心

## 1. 面试先给结论

Nacos 在 Spring Cloud Alibaba 体系里主要承担两个职责：

- 注册中心：服务实例注册、服务发现、健康检查。
- 配置中心：集中管理配置、动态刷新配置、多环境隔离。

面试表达可以这样说：

> Nacos 解决的是微服务之间如何找到彼此，以及配置如何集中管理的问题。服务启动后会把自己的 IP、端口、服务名注册到 Nacos，调用方通过服务名获取实例列表，再结合负载均衡选择一个实例调用。配置中心则把数据库地址、开关、限流阈值等配置从应用包中抽离出来，便于多环境管理和动态调整。

## 2. 为什么需要注册中心

单体应用中，模块之间是本地方法调用。

微服务拆分后，服务之间变成远程调用。调用方需要知道：

- 目标服务有哪些实例。
- 每个实例的 IP 和端口是什么。
- 哪些实例可用。
- 实例上下线后如何感知。

如果不使用注册中心，只能在配置文件里写死地址：

```yaml
user-service:
  url: http://192.168.1.10:8081
```

这种方式的问题：

- 服务扩容后要手动改配置。
- 服务下线后调用方不一定知道。
- IP 变化后需要重新发布。
- 多环境维护困难。

注册中心的价值：

- 服务自动注册。
- 服务自动发现。
- 实例上下线自动感知。
- 支持负载均衡。
- 降低服务地址维护成本。

## 3. Nacos 注册发现基本流程

### 3.1 服务注册

服务启动后，会把自己的信息注册到 Nacos：

- 服务名。
- IP。
- 端口。
- 分组。
- 命名空间。
- 权重。
- 健康状态。
- 元数据。

例如：

```text
sync-producer-service -> 192.168.1.20:8081
sync-consumer-service -> 192.168.1.21:8082
query-service         -> 192.168.1.22:8083
```

### 3.2 服务发现

调用方不再写死 IP，而是通过服务名调用。

例如：

```text
http://sync-consumer-service/api/sync/retry
```

客户端会从 Nacos 获取 `sync-consumer-service` 的实例列表，再通过负载均衡选择一个实例。

### 3.3 健康检查

Nacos 会判断实例是否健康。

常见方式：

- 临时实例：客户端通过心跳续约。
- 非临时实例：服务端主动探测。

Spring Cloud Alibaba 中常见的是临时实例。服务需要定期向 Nacos 发送心跳，如果长期没有心跳，Nacos 会认为实例不健康或下线。

## 4. 临时实例和非临时实例

### 4.1 临时实例

临时实例适合普通微服务应用。

特点：

- 服务启动后注册。
- 服务停止或心跳超时后自动摘除。
- 适合弹性扩缩容。
- 默认更常用。

### 4.2 非临时实例

非临时实例适合比较固定的服务。

特点：

- 实例不会因为心跳丢失立即删除。
- 通常需要服务端探测健康状态。
- 更适合固定节点管理。

面试中一般不用展开太深，能说明“临时实例靠心跳，适合微服务弹性上下线”即可。

## 5. 服务发现与负载均衡

Nacos 负责提供实例列表，负载均衡组件负责选择实例。

调用过程：

1. 服务 A 调用服务 B。
2. 服务 A 根据服务名从本地缓存或 Nacos 获取 B 的实例列表。
3. 负载均衡选择一个实例。
4. 发起 HTTP/RPC 调用。

常见负载均衡策略：

- 轮询。
- 随机。
- 权重。
- 就近访问。

Nacos 本身也支持权重配置。

例如：

```text
query-service
- 192.168.1.10:8080 weight=1
- 192.168.1.11:8080 weight=3
```

权重高的实例会承担更多流量。

## 6. 注册中心宕机后还能调用吗

这是高频问题。

答案：

> 已经发现过的服务，通常还能继续调用，因为客户端会缓存服务实例列表。但新服务注册、实例下线感知、配置变更会受影响。所以注册中心不能单点部署，生产环境要做集群。

要点：

- Nacos 宕机不等于业务立刻不可用。
- 客户端本地缓存可以支撑已有调用。
- 新实例注册可能失败。
- 下线实例可能不能及时摘除。
- 配置中心变更不可用。
- 生产要集群部署。

面试表达：

> 如果 Nacos 短时间不可用，客户端本地缓存的实例列表还能支撑已有服务调用。但这不是高可用方案，因为实例上下线和配置更新会受影响。生产环境需要 Nacos 集群部署，同时服务调用侧要设置合理超时、重试和熔断。

## 7. 为什么需要配置中心

如果配置都写在应用包里，会有几个问题：

- 修改配置需要重新打包发布。
- 多环境配置容易混乱。
- 敏感配置不方便统一管理。
- 开关、阈值不能动态调整。
- 多个实例配置不一致。

配置中心适合管理：

- 数据库连接。
- Redis 地址。
- Kafka 地址。
- 开关配置。
- 限流阈值。
- 业务规则参数。
- 第三方接口地址。
- 超时时间。

不建议频繁放入配置中心的内容：

- 大段业务数据。
- 每次请求都会变化的数据。
- 需要强审计的核心密钥明文。

## 8. Nacos 配置模型

Nacos 配置常见维度：

- Namespace：环境隔离。
- Group：业务或项目分组。
- Data ID：具体配置文件。

### 8.1 Namespace

常用于环境隔离：

- dev。
- test。
- pre。
- prod。

不同环境配置互不影响。

### 8.2 Group

常用于项目或业务分组：

- DEFAULT_GROUP。
- SYNC_GROUP。
- QUERY_GROUP。

### 8.3 Data ID

具体配置文件名。

例如：

```text
sync-service-dev.yaml
query-service-prod.yaml
common-redis.yaml
```

## 9. Spring Boot 接入 Nacos 的典型配置

示例：

```yaml
spring:
  application:
    name: sync-consumer-service
  cloud:
    nacos:
      discovery:
        server-addr: 127.0.0.1:8848
        namespace: dev
        group: SYNC_GROUP
      config:
        server-addr: 127.0.0.1:8848
        namespace: dev
        group: SYNC_GROUP
        file-extension: yaml
```

说明：

- `spring.application.name` 是服务注册名。
- `discovery` 配置注册发现。
- `config` 配置配置中心。
- `namespace` 用于环境隔离。
- `group` 用于业务分组。

## 10. 动态配置刷新

配置中心常见用途是动态调整开关和阈值。

例如：

```yaml
sync:
  retry:
    max-count: 3
  consumer:
    enabled: true
```

项目中可以用于：

- 开关某类同步任务。
- 调整补偿任务批次大小。
- 调整最大重试次数。
- 调整接口超时时间。
- 调整限流阈值。

注意：

- 动态刷新适合开关、阈值类配置。
- 数据源连接池、线程池核心参数不一定都适合直接动态改。
- 生产配置变更要有审计和回滚记录。

## 11. Nacos 在数据同步平台中的用法

你的数据同步平台可以这样包装：

### 11.1 注册发现

服务拆分后：

- `sync-producer-service`：同步消息生产服务。
- `sync-consumer-service`：同步消费处理服务。
- `sync-compensation-service`：补偿任务服务。
- `sync-admin-service`：同步管理后台。

这些服务启动后注册到 Nacos。

调用关系：

```text
sync-admin-service -> sync-compensation-service
sync-admin-service -> sync-consumer-service
sync-producer-service -> Kafka
sync-consumer-service -> source-db / target-db
```

面试表达：

> 如果这个数据同步平台继续演进，我会把生产、消费、补偿、管理能力拆成独立服务，并通过 Nacos 做服务注册发现。这样补偿服务和消费服务可以独立扩容，管理端不需要写死服务地址。

### 11.2 配置中心

可以放到 Nacos 的配置：

- Kafka broker 地址。
- topic 名称。
- consumer group。
- 消费开关。
- 单批次补偿数量。
- 最大重试次数。
- 失败告警开关。
- 下游接口超时时间。

示例：

```yaml
sync:
  kafka:
    topic: gov-data-sync
    consumer-group: gov-data-sync-consumer
  compensation:
    enabled: true
    batch-size: 100
    max-retry-count: 5
  alarm:
    enabled: true
```

面试表达：

> 对于数据同步项目，我会把同步开关、补偿批次、最大重试次数、告警开关这类配置放到 Nacos。这样线上出现积压或下游异常时，可以先通过配置降低批量、暂停部分任务或打开告警，不一定每次都重新发版。

## 12. Nacos 在中考查询系统中的用法

可拆分服务：

- `exam-query-service`：考生成绩查询。
- `exam-admin-service`：后台管理。
- `exam-data-service`：成绩数据维护。
- `exam-notice-service`：通知服务。

配置中心可管理：

- 查询开关。
- 查询开放时间。
- 限流阈值。
- Redis key 前缀。
- 缓存 TTL。
- 降级开关。

示例：

```yaml
exam:
  query:
    enabled: true
    start-time: 2026-07-01 09:00:00
    end-time: 2026-07-05 18:00:00
    rate-limit: 2000
  cache:
    ttl-seconds: 600
```

面试表达：

> 中考查询系统中，Nacos 配置中心可以管理查询开放时间、限流阈值、缓存 TTL 和降级开关。这样高峰期如果访问量超过预期，可以动态调整限流或缓存策略，减少重新发布带来的风险。

## 13. Nacos 常见生产问题

### 13.1 服务注册不上

排查方向：

- `server-addr` 是否正确。
- namespace 是否正确。
- group 是否一致。
- 网络是否通。
- 服务名是否配置。
- Nacos 权限是否开启。

### 13.2 服务能注册但调用失败

排查方向：

- 实例 IP 是否是内网可访问 IP。
- 防火墙端口是否放通。
- 服务端口是否正确。
- 健康状态是否正常。
- 调用方是否使用正确服务名。

### 13.3 配置不生效

排查方向：

- Data ID 是否正确。
- namespace/group 是否一致。
- 文件后缀是否匹配。
- 是否开启动态刷新。
- 本地配置是否覆盖远程配置。

### 13.4 配置变更引发线上问题

处理方式：

- 配置变更要有审批。
- 关键配置要灰度。
- 保留变更记录。
- 可以快速回滚。
- 重要阈值变更要配合监控。

## 14. 面试高频问题

### 14.1 Nacos 注册中心的作用是什么

答法：

> Nacos 注册中心负责服务注册和服务发现。服务启动时把自己的 IP、端口、服务名注册到 Nacos，调用方通过服务名获取实例列表，再结合负载均衡选择实例调用。这样服务扩容、下线、IP 变化时，不需要调用方写死地址。

### 14.2 Nacos 配置中心的作用是什么

答法：

> 配置中心用于集中管理多环境、多服务配置，把数据库、Redis、Kafka、开关、阈值等配置从应用包里抽离出来。这样可以减少重新发版，也方便动态调整和统一管理。

### 14.3 Nacos 宕机后服务还能调用吗

答法：

> 短时间内一般还能调用已缓存的服务实例，但新服务注册、实例下线感知、配置更新会受影响。所以生产环境要做 Nacos 集群，同时服务调用侧也要有超时、熔断和重试保护。

### 14.4 Namespace、Group、Data ID 分别是什么

答法：

> Namespace 通常做环境隔离，比如 dev、test、prod。Group 通常做项目或业务分组。Data ID 是具体配置文件，比如 sync-service-prod.yaml。

### 14.5 注册中心和网关有什么区别

答法：

> 注册中心解决服务之间如何发现彼此的问题，网关解决外部请求如何统一进入系统的问题。注册中心偏内部服务治理，网关偏入口路由、鉴权、限流、跨域和统一日志。
