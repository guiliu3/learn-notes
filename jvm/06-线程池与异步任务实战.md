# 06-线程池与异步任务实战

## 1. 面试先给结论

线程池不是为了让任务无限并发，而是为了复用线程、控制并发、隔离资源、保护系统。8 年 Java 面试里，线程池一定要能讲参数、提交流程、拒绝策略、为什么不用 Executors，以及项目里怎么设置。

面试表达可以这样说：

> 我理解线程池的核心是控制资源。任务提交后先创建核心线程，核心线程满了进队列，队列满了再创建非核心线程，达到最大线程数后执行拒绝策略。生产环境我不会直接用 Executors，而是用 ThreadPoolExecutor 显式配置核心线程数、最大线程数、有界队列、线程命名和拒绝策略。

## 2. 线程池七个参数

```java
ThreadPoolExecutor(
    int corePoolSize,
    int maximumPoolSize,
    long keepAliveTime,
    TimeUnit unit,
    BlockingQueue<Runnable> workQueue,
    ThreadFactory threadFactory,
    RejectedExecutionHandler handler
)
```

说明：

- corePoolSize：核心线程数。
- maximumPoolSize：最大线程数。
- keepAliveTime：非核心线程空闲存活时间。
- unit：时间单位。
- workQueue：任务队列。
- threadFactory：线程工厂。
- handler：拒绝策略。

## 3. 任务提交流程

流程：

1. 当前工作线程数小于 corePoolSize，创建核心线程执行任务。
2. 核心线程已满，任务进入阻塞队列。
3. 队列满了，且线程数小于 maximumPoolSize，创建非核心线程。
4. 队列满且线程数达到 maximumPoolSize，执行拒绝策略。

重点：

> 不是先创建到最大线程数，再放队列。默认流程是核心线程 -> 队列 -> 最大线程 -> 拒绝策略。

## 4. 为什么不用 Executors

`Executors.newFixedThreadPool`：

- 使用无界 LinkedBlockingQueue。
- 任务可能无限堆积，导致 OOM。

`Executors.newCachedThreadPool`：

- 最大线程数接近无限。
- 可能创建大量线程，导致 OOM 或上下文切换严重。

`Executors.newSingleThreadExecutor`：

- 使用无界队列。
- 单线程处理慢时任务无限堆积。

面试表达：

> Executors 的问题是隐藏了队列和线程数风险。生产中我更倾向于手动创建 ThreadPoolExecutor，使用有界队列、明确线程数、线程名称和拒绝策略，这样系统超过承载能力时能及时暴露，而不是一直堆任务。

## 5. 队列怎么选

### 5.1 ArrayBlockingQueue

- 有界数组队列。
- 适合生产。
- 能控制任务积压。

### 5.2 LinkedBlockingQueue

- 链表队列。
- 可以有界，也可以无界。
- 无界时风险较大。

### 5.3 SynchronousQueue

- 不存储任务。
- 任务必须直接交给线程。
- 适合短任务、高弹性场景。

### 5.4 PriorityBlockingQueue

- 优先级队列。
- 注意任务饥饿和无界风险。

## 6. 拒绝策略怎么选

### 6.1 AbortPolicy

直接抛异常。

适合：

- 希望调用方感知失败。
- 关键任务需要记录失败。

### 6.2 CallerRunsPolicy

调用方线程自己执行任务。

效果：

- 降低提交速度。
- 形成反压。

适合：

- 不希望任务丢失。
- 可以接受调用方变慢。

### 6.3 DiscardPolicy

直接丢弃，不抛异常。

风险：

- 静默丢任务。

### 6.4 DiscardOldestPolicy

丢弃队列最老任务。

风险：

- 老任务丢失。

面试表达：

> 生产中我很少用静默丢弃策略。关键业务任务被拒绝后要记录日志、失败表或告警。非核心统计类任务可以考虑丢弃，但要明确业务允许。

## 7. 线程池参数怎么估

不能只背公式。

要看：

- CPU 核数。
- 任务是 CPU 密集还是 IO 密集。
- QPS。
- 平均 RT。
- 下游数据库连接池。
- Redis/HTTP 连接池。
- 单机资源。
- 失败后的降级策略。

### 7.1 CPU 密集型

线程数接近 CPU 核数。

例如：

```text
CPU 核数 + 1
```

### 7.2 IO 密集型

线程数可以大于 CPU 核数，因为线程经常等待 IO。

但不能无限大，要受下游约束。

例如数据库连接池只有 30 个，写库线程池开 200 没意义，只会造成等待和超时。

## 8. 线程池隔离

不同任务不要共用一个线程池。

应该隔离：

- Web 请求线程。
- 业务异步任务。
- Kafka 消费任务。
- 补偿任务。
- 通知任务。
- 报表任务。

好处：

- 防止非核心任务拖垮核心链路。
- 便于监控。
- 便于限流。
- 便于故障隔离。

## 9. 中考查询系统怎么讲

场景：

- 高峰查询。
- 异步查询。
- 查询结果缓存。
- 通知或日志记录。

设计：

- Web 请求线程不做重任务。
- 查询任务线程池独立。
- 队列有界。
- 线程池满时返回“查询繁忙”或“查询中”。
- 非核心日志和通知使用独立线程池。
- 配合 Sentinel 限流。

面试表达：

> 中考查询系统里，我会把查询主链路和非核心异步任务隔离。Web 请求线程不能被慢查询长期占用，异步查询线程池要有界队列和拒绝策略。超过系统承载能力时，宁愿返回查询繁忙，也不能让任务无限堆积把 JVM 内存打满。

## 10. 数据同步平台怎么讲

场景：

- Kafka 实时消费。
- 失败补偿。
- 告警通知。
- 人工重推。

设计：

- 实时消费线程池和补偿线程池隔离。
- 补偿任务限流，不能抢占实时消费资源。
- 写库并发受数据库连接池限制。
- 批量任务分批提交。
- 失败进入失败表或 DLQ。

面试表达：

> 数据同步平台里，实时消费和补偿任务必须隔离。否则补偿任务一多，会抢占线程池和数据库连接，导致正常消费也变慢。线程池参数要结合 Kafka 分区数、消费者实例数、数据库连接池和目标库写入能力设置，不能盲目加线程。

## 11. 线程池监控指标

需要关注：

- corePoolSize。
- maximumPoolSize。
- activeCount。
- poolSize。
- queueSize。
- completedTaskCount。
- rejectedCount。
- taskCostTime。

如果发现：

- activeCount 长期接近 maximumPoolSize。
- queueSize 持续增长。
- rejectedCount 增加。

说明线程池可能已达到瓶颈。

## 12. 高频问题

### 12.1 线程池任务提交流程

答法：

> 先判断线程数是否小于核心线程数，小于则创建核心线程；否则尝试入队；队列满了且线程数小于最大线程数，则创建非核心线程；如果队列满且达到最大线程数，就执行拒绝策略。

### 12.2 为什么不用 Executors

答法：

> Executors 容易隐藏无界队列或无限线程数风险，任务堆积可能 OOM。生产更推荐 ThreadPoolExecutor 显式配置线程数、有界队列、线程工厂和拒绝策略。

### 12.3 线程池队列为什么要有界

答法：

> 无界队列会把压力隐藏起来，任务不断堆积，最终可能 OOM 或延迟失控。有界队列能让系统超过承载能力时及时触发拒绝策略。

### 12.4 线程池满了怎么办

答法：

> 先看是任务太慢、下游慢、线程数太小还是流量过大。处理上可以优化慢任务、限流、降级、拆分线程池、调整参数。不能只盲目加线程，因为可能压垮下游。

## 13. 你要背下来的 1 分钟版本

> 线程池用于复用线程、控制并发和资源隔离。任务提交后先创建核心线程，核心线程满了进队列，队列满了再创建非核心线程，达到最大线程数后执行拒绝策略。生产不建议用 Executors，因为可能有无界队列或无限线程风险。参数要结合 CPU、QPS、RT、任务类型和下游数据库连接池设置。线程池队列必须有界，核心任务和非核心任务要隔离，拒绝后要有日志、告警或补偿。
